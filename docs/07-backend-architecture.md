# Ant Design Pro 大型 SaaS 系统后端架构与基础设施规范

> 说明：这份文档保留了早期后端底座的设计约束与演进思路。当前仓库主线已经进入 Spring Cloud Alibaba 微服务骨架阶段，最新目标请以 [docs/12-microservice-restructure.md](./12-microservice-restructure.md) 为准。

## 1. 文档定位

本规范用于统一后端总体架构、分层模式、模块边界、基础设施接入、数据访问约束、缓存体系、限流策略、异步任务、文件存储、日志审计、配置管理、可观测体系以及高可用与可演进策略。

它不是单纯的技术选型说明，而是整套平台底座的工程规范。

## 2. 总体目标

- 建立清晰的模块化底座。
- 建立多租户上下文机制。
- 建立高可靠保护机制。
- 建立统一基础设施接入方式。
- 建立清晰的演进路径。

## 3. 架构原则

- 微服务平台优先。
- 基础设施统一收敛。
- 主干链路优先。
- 边界先于实现。
- 可观测性内建。

## 4. 技术路线建议

建议使用：

- `Java 21`
- `Spring Boot 4.0.6`
- `Spring Cloud 2025.1.1`
- `Spring Cloud Alibaba 2025.1.0.0`
- `Spring Security`
- `MyBatis Plus`
- `MySQL 8`
- `Redis`
- `Nacos`
- `Sentinel`
- `XXL-JOB`
- `Seata`
- `Springdoc OpenAPI`

当前仓库已经进入微服务骨架阶段，早期“先把单体底座做稳”的描述仅作为演进背景；新增能力应优先落在明确的服务边界上。

## 5. 分层架构

后端建议分为四层：

- 接口接入层：HTTP 接口、参数接收、返回封装、认证入口、请求上下文。
- 应用服务层：用例编排。
- 领域规则层：业务规则、状态流转、约束判断。
- 基础设施层：数据库、缓存、对象存储、消息队列、任务调度、租户拦截、日志上报。

## 6. 模块边界

建议至少拆分以下核心模块：

- `auth`：登录、登出、刷新、会话、多端控制、登录日志。
- `tenant`：租户生命周期、状态、套餐、配额、域名、初始化、切换。
- `iam`：角色、菜单、按钮权限、接口权限、数据范围、权限快照。
- `user` / `org`：用户、用户租户关系、部门、岗位。
- `dict`：平台字典、租户字典、缓存刷新。
- `config`：平台配置、租户配置、加密、审计。
- `file`：上传、下载、元数据、预签名、配额。
- `message`：站内信、模板消息、发送记录、异步通知。
- `task`：导入导出、报表、异步作业、重试控制。
- `audit`：操作日志、登录日志、权限变更日志、高风险动作审计。

## 7. 多租户上下文

- 租户上下文是一级上下文。
- 任何请求都应在认证后建立当前租户上下文。
- 上下文至少应包含租户 ID、租户编码、租户状态、用户 ID、角色集、权限快照版本。
- 租户隔离应同时落在数据、缓存、对象存储、日志、任务和限流层。

### 7.1 租户识别顺序

建议优先顺序：

1. 从 token 或会话解析租户。
2. 必要时校验请求头中的租户标识。
3. 平台入口或租户切换接口可显式指定目标租户。
4. 开放接口或内部任务按专门规则解析。

服务端必须验证当前用户是否真的有资格进入该租户。

## 8. 认证与会话

- 建议采用 `Access Token + Refresh Token + Redis 会话控制` 的混合模式。
- Access Token 用于接口访问。
- Refresh Token 用于刷新登录态。
- Redis 会话用于记录会话状态、租户上下文版本、权限快照版本和踢下线控制。
- 需预留单端登录、多端登录限制和高敏感账号更强会话控制能力。

## 9. 数据访问

- 建议以 MyBatis Plus 处理基础单表能力。
- 复杂查询用手写 SQL 保证可控性。
- 所有租户级查询必须自动附带 `tenant_id`。
- 列表查询必须分页。
- 高频列表要结合索引设计。
- 批量更新删除必须防止全表误操作。
- 复杂报表不应直接压事务主表。

## 10. 缓存体系

建议采用两层缓存：

- 本地热点缓存：字典元信息、极高频只读配置、少量固定元数据。
- Redis 分布式缓存：会话、权限快照、租户配置、菜单树、字典项、热点查询结果、限流计数、任务状态。

缓存 key 必须显式包含环境、模块、租户、用户等维度。角色变更、菜单变更、租户切换、配置修改、字典更新、租户停用、用户移出租户等场景必须触发失效或版本刷新。

## 11. 限流与防刷

至少支持以下维度：

- IP 维度
- 用户维度
- 租户维度
- 接口维度
- 客户端维度
- 全局维度

登录、导出、提交任务、状态切换等高风险动作必须支持防重复提交或幂等控制。

## 12. 异步任务与削峰

统一任务中心应覆盖：

- 导入导出
- 报表生成
- 批量消息
- 批量授权
- 文件处理
- 同步任务
- 定时汇总

任务至少应包含任务创建、状态、结果、失败原因、重试次数、执行日志和取消能力，并记录 `tenant_id` 与 `user_id`。

## 13. 文件与对象存储

- 文件能力必须平台化。
- 上传、下载、删除、元数据记录、配额校验和访问控制应由统一文件中心承载。
- 对象存储路径建议按环境、租户、业务模块、日期分层。
- 私有文件默认不能裸链访问，应通过预签名或受控下载接口。
- 重要文件必须强制落库元数据。

## 14. 日志与审计

### 14.1 应用日志

应用日志至少包含 `traceId`、`tenantId`、`userId`、`requestId`、接口路径、耗时、结果码等上下文。

### 14.2 操作审计

用户管理、角色分配、权限调整、租户切换、配置修改、导入导出、敏感状态变更都必须进入审计日志。

### 14.3 安全日志

登录成功、登录失败、登出、刷新 token、账号锁定、异常切换尝试、权限拒绝等应单独记录。

### 14.4 脱敏

日志中不得直接记录密码、完整 token、完整身份证号、完整手机号等敏感信息。

## 15. 异常处理

- 系统必须有统一全局异常处理器。
- 参数异常、业务异常、权限异常、租户异常、限流异常、依赖异常和系统异常都应转换为标准响应结构。
- 所有异常必须带 `requestId` 或 `traceId`。

## 16. 配置管理

配置至少分三层：

- 环境配置
- 平台配置
- 租户配置

配置读取统一走配置中心模块，不允许各处自行查表或自行拼缓存。敏感配置必须支持加密存储与审计。

## 17. 可观测性

至少暴露以下指标：

- HTTP 请求数、成功率、错误率、RT
- JVM、GC、线程池、CPU
- 数据库连接池、慢 SQL
- Redis 命中率、延迟
- 消息队列堆积量
- 任务成功率和失败率
- 租户级流量与资源消耗

需要链路追踪贯穿跨模块调用、异步任务、文件处理和权限快照生成。

## 18. 高可靠策略

- 主链路优先保护。
- 弱依赖异常应允许降级而不是拖垮主业务。
- 外部依赖异常时需要熔断或隔离。
- 所有外部访问必须设置明确超时。

## 19. 部署与运行

第一阶段建议采用容器化模块化单体，至少支持：

- Nginx 或云负载均衡
- 2 个及以上应用实例
- Redis 高可用或主从
- MySQL 主库 + 备份恢复机制
- 独立对象存储
- 日志与监控平台

应用实例必须尽量无状态，部署流程要支持版本化、灰度和快速回滚。

## 20. 演进路径

### 20.1 第一阶段

先把认证、租户、IAM、用户组织、字典配置、文件、任务、审计这些底座模块做稳。

### 20.2 第二阶段

当某些模块职责独立或流量升高时，可按边界逐步拆分，例如文件中心、消息中心、任务中心、开放接口网关等。

### 20.3 第三阶段

针对重点租户逐步增强独立库、独立缓存前缀、独立文件空间甚至独立部署形态。

## 21. 第一阶段建设清单

- 统一认证与会话中心
- 租户上下文解析与切换
- 统一 RBAC 与数据范围过滤
- 统一异常处理与错误码体系
- 统一 MyBatis 数据访问规范
- 统一 Redis 缓存封装
- 统一限流与防重复提交组件
- 统一文件中心
- 统一异步任务中心
- 统一日志、审计与链路追踪
- 统一配置中心
- 统一健康检查与监控指标暴露

## 22. 开发红线

- 严禁业务代码手工拼 `tenant_id` 作为长期隔离方案。
- 严禁控制器直接操作 mapper。
- 严禁每个模块自己实现一套缓存 key 规则。
- 严禁把导入导出做成同步阻塞接口。
- 严禁把文件直接落本地磁盘作为正式方案。
- 严禁异常原样返回堆栈给前端。
- 严禁核心写操作没有审计日志。
- 严禁缓存、数据库、对象存储等依赖无超时控制。
- 严禁权限校验只做前端不做后端。
- 严禁租户切换后不刷新权限与上下文。

## 23. 实施结论

这份规范的核心，是把后端做成稳定、清晰、可治理、可扩展的工程底座。

前期坚持模块化单体，统一基础设施，保护主链路，内建可观测，后续再按边界演进拆分，这样才适合大型 SaaS 系统长期运行。
