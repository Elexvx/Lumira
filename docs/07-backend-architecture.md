# Legendary Invention 项目后端开发规范

## 1. 文档定位

本文档是 Legendary Invention 项目的后端开发规范，适用于当前仓库中的 `services/` 与 `libs/` 模块。

本文档以当前项目实际形态为准：代码按多模块拆分，运行入口以 `services/legendary-server` 聚合启动为主。也就是说，设计上保留服务边界，运行上以聚合服务承载主线能力。

## 2. 适用范围

- 适用于 `services/*` 下所有业务模块和聚合启动模块。
- 适用于 `libs/*` 下公共能力模块。
- 适用于控制器、应用服务、领域逻辑、数据访问、缓存、消息、任务、日志、审计和配置代码。

## 3. 当前项目基线

### 3.1 当前模块结构

根 `pom.xml` 与各模块结构表明，当前项目包含如下主要模块：

- 启动聚合：`services/legendary-server`
- 业务服务：`system-service`、`auth-service`、`file-service`、`message-service`、`plugin-service`、`localization-service`、`payment-service`、`job-executor`
- 公共库：`common-core`、`common-domain`、`common-web`、`common-security`、`legendary-api`、`plugin-api`

### 3.2 当前技术栈

根据 `pom.xml` 当前基线如下：

- `Java 21`
- `Spring Boot 4.0.6`
- `Spring Cloud 2025.1.1`
- `Spring Cloud Alibaba 2025.1.0.0`
- `MyBatis Plus 3.5.16`
- `Flyway 12.5.0`
- `MySQL Connector/J 9.7.0`
- `Spring Security`
- `OpenTelemetry API 1.50.0`

### 3.3 当前运行方式

当前默认运行方式不是将所有模块独立部署，而是通过 `legendary-server` 聚合：

- 对外主入口统一
- 内部代码边界保留
- 后续可根据流量、职责、部署需要再做物理拆分

因此，后端开发必须同时满足两个目标：

1. 单次部署可运行
2. 模块边界不被写坏

### 3.4 单体微服务运行基线

当前仓库主线采用“单体微服务”模式：运行时收敛为一个后端进程 `services/legendary-server`，工程内继续保留 `services/*-service` 的模块边界、契约边界和数据 owner。

这意味着：

1. 不是回到历史大单体随意耦合。
2. 也不是默认要求每个服务独立部署。
3. 当前唯一推荐后端启动入口是 `services/legendary-server`。
4. 各业务服务模块是未来可物理拆分的边界，不允许在聚合运行阶段把边界写坏。

### 3.5 聚合运行与部署约束

当前后端聚合运行至少遵循以下约束：

1. `services/legendary-server` 是正式 Spring Boot 启动入口。
2. 聚合模式下，对外主 API 入口统一。
3. `api-proxy` 统一暴露 `/api/**`、`/ws/**` 等对外路径时，上游应指向聚合服务。
4. 当前默认不以 Nacos 服务发现作为本地开发前提，相关配置仅为后续拆分预留。
5. 敏感配置只能通过环境变量或密钥系统注入，不能硬编码进仓库。

### 3.6 运行与启动顺序基线

后端联调和部署说明中，默认启动顺序应保持一致：

1. 启动 MySQL、Redis、XXL-JOB Admin 等基础依赖
2. 启动 `services/legendary-server`
3. 启动 `api-proxy`
4. 启动前端
5. 按需启动 Prometheus、Grafana、Loki、Tempo 等观测组件

### 3.7 后续拆分原则

后续如果从聚合模式拆分为独立服务，建议优先从低耦合、owner 清晰、外部副作用较少的模块开始，例如：

1. `file-service`
2. `message-service`
3. `localization-service`
4. `plugin-service`
5. `auth-service`
6. `job-executor`
7. `system-service`

拆分任何一个模块时，必须同时补齐：

- 独立启动能力
- 独立配置
- 健康检查
- 部署编排
- API 路由
- 契约调用
- 数据 owner
- 迁移脚本
- 回滚方案

### 3.8 不允许的架构形态

后端演进过程中明确禁止以下做法：

1. 新增历史 `backend` 大单体入口。
2. 同一业务同时维护“聚合模块实现”和“独立服务实现”两份长期并存逻辑。
3. 为了拆服务而直接跨库读写别的 owner 表。
4. 只拆 Docker 容器，不拆契约、数据 owner 和权限边界。

## 4. 后端总体原则

1. 先保证边界清晰，再追求实现速度。
2. 先保证统一契约，再追求局部灵活。
3. 控制器只做接入，不承载业务编排。
4. 多租户、权限、审计、异常、缓存都是平台级能力，不允许各模块私自发明新规则。
5. 新增代码应优先复用 `libs/*` 公共能力，不重复造轮子。

## 5. 模块划分规范

## 5.1 服务模块职责

各服务模块应围绕明确职责演进：

| 模块 | 主要职责 |
| --- | --- |
| `system-service` | 系统管理、用户、角色、菜单、权限、字典、配置、仪表盘、在线会话等 |
| `auth-service` | 登录、令牌、会话、登录保护、Passkey、验证码、二次验证等 |
| `file-service` | 文件上传、下载、元数据、存储空间、文件安全控制 |
| `message-service` | 站内消息、通知、投递日志、WebSocket 票据与分发 |
| `plugin-service` | 插件定义、插件版本、租户插件关系、运行时安全策略 |
| `localization-service` | 国际化语言、命名空间、词条、发布与引用 |
| `payment-service` | 支付订单、退款、支付服务商配置、Webhook |
| `job-executor` | 异步任务、outbox relay、系统级后台作业 |

## 5.2 公共库职责

| 模块 | 主要职责 |
| --- | --- |
| `common-core` | 通用常量、响应结构、错误码、基础 VO/DTO |
| `common-domain` | 领域通用抽象与共享模型 |
| `common-web` | Web 层公共能力、异常处理、Trace、RepeatSubmit |
| `common-security` | JWT、安全上下文、字段加解密、数据权限 |
| `legendary-api` | 跨模块 API DTO 与客户端契约 |
| `plugin-api` | 插件 SPI 与插件运行时接口 |

## 5.3 依赖方向

必须遵守以下依赖方向：

1. 业务模块依赖公共库。
2. 聚合启动模块依赖业务模块。
3. 公共库不能反向依赖业务模块。
4. 一个业务模块不应直接读写另一个业务模块的私有持久化实现。

## 6. 分层开发规范

## 6.1 标准分层

每个服务模块内部建议统一按以下分层理解代码职责：

1. 接口接入层：Controller、请求 DTO、返回 VO、鉴权注解入口。
2. 应用服务层：面向用例编排，负责事务边界、权限前置、调用顺序。
3. 领域与规则层：核心规则、状态流转、校验、聚合行为。
4. 基础设施层：Mapper、SQL、缓存、消息、对象存储、外部集成。

## 6.2 Controller 规范

Controller 只负责：

- 接收参数
- 触发校验
- 调用应用服务
- 返回统一响应

Controller 禁止直接：

- 写复杂业务逻辑
- 直接拼 SQL
- 直接操作多张表事务
- 直接决定缓存策略

## 6.3 应用服务规范

应用服务是用例编排中心，负责：

- 组织一次完整业务操作
- 确定事务边界
- 调用领域服务和持久化能力
- 统一记录审计
- 统一触发事件或任务

## 6.4 DTO / VO / Entity 边界

- Request DTO：只面向接入层。
- Response VO / DTO：只面向出参或跨模块契约。
- Entity：只面向持久化层。
- 禁止把 Entity 直接作为接口返回。

## 7. 接口与响应规范

## 7.1 统一响应

后端统一使用公共响应结构，相关能力应复用 `common-core` 中的 `ApiResponse`、分页对象和错误码定义。

## 7.2 接口命名

- 路径按资源语义命名，不按页面按钮命名。
- 读写动作遵循 HTTP 语义。
- 内部接口、公共接口、租户接口应明确隔离。

## 7.3 参数校验

- 入参必须做 Bean Validation 或等价校验。
- 字段长度、格式、枚举范围、必填性必须在接入层尽早拦截。
- 复杂业务合法性判断放在应用服务或领域层。

## 8. 认证、权限与租户规范

## 8.1 认证规范

当前项目已有 JWT、安全上下文、会话与登录保护相关能力，新增认证相关代码必须复用统一安全体系，不另起一套会话机制。

## 8.2 权限规范

- 菜单权限、按钮权限、接口权限、数据权限必须区分清楚。
- 前端显隐不构成后端授权。
- 高风险动作必须在服务端再次校验。

## 8.3 租户上下文规范

租户是一级上下文，所有租户级请求必须在进入业务逻辑前建立租户上下文。

上下文至少要能识别：

- 当前租户
- 当前用户
- 当前角色集
- 当前权限快照

## 8.4 租户切换规范

租户切换相关能力必须同时考虑：

- 会话中的租户上下文刷新
- 权限快照刷新
- 缓存失效
- 审计留痕

## 9. 数据访问规范

## 9.1 基本原则

- 基础 CRUD 优先用 MyBatis Plus。
- 复杂查询允许手写 SQL。
- 手写 SQL 必须可读、可维护、可审查。
- 列表查询必须分页。

## 9.2 Mapper 规范

- Mapper 只负责持久化，不承载业务编排。
- 复杂 SQL 必须配合清晰命名和必要注释。
- SQL 条件必须显式考虑逻辑删除和租户边界。

## 9.3 SQL 编写要求

- 禁止字符串拼接形成不受控 SQL。
- `IN` 查询必须做好空集合保护。
- 更新和删除必须具备明确 where 条件。
- 任何批量写入都要考虑误操作范围。

## 9.4 事务规范

- 事务放在应用服务层边界。
- 只对真正需要原子性的流程加事务。
- 外部调用、消息发送、文件 IO 等长耗时动作要谨慎放入同一事务。

## 10. 缓存规范

## 10.1 缓存适用场景

缓存主要用于：

- 会话状态
- 权限快照
- 租户配置
- 字典项
- 菜单树
- 热点只读数据
- 限流计数
- 任务状态

## 10.2 Key 规范

缓存 key 至少要体现：

- 环境
- 模块
- 资源类型
- 租户维度
- 用户维度或对象维度

## 10.3 失效规范

以下场景必须明确刷新或失效策略：

- 角色变更
- 菜单变更
- 权限变更
- 租户切换
- 配置变更
- 字典变更
- 用户状态变更

## 11. 文件、消息与异步任务规范

## 11.1 文件规范

- 文件元数据必须通过统一文件中心落库。
- 文件访问必须受权限和租户控制。
- 私有文件不得直接暴露裸链。
- 上传成功与业务记录关联要有明确流程。

## 11.2 消息规范

- 站内消息、通知投递、投递日志必须区分。
- 消息发送失败要记录原因，便于补偿。
- WebSocket、SSE、站内信等实时链路要考虑鉴权与票据有效期。

## 11.3 异步任务规范

- 导入导出、批量通知、对账、重试、事件投递优先走任务机制。
- 任务必须可追踪状态。
- 任务必须记录租户和触发人信息。

## 11.4 Outbox 规范

当前项目已有 `platform_event_outbox` 相关实现，跨模块事件投递应优先复用 outbox 模式，避免“主事务成功但事件丢失”的不一致。

## 12. 审计、日志与异常规范

## 12.1 审计规范

以下操作原则上必须审计：

- 登录与登出
- 用户新增、停用、删除、重置密码
- 角色与权限调整
- 租户切换
- 配置修改
- 文件删除与敏感下载
- 支付配置修改
- 插件安装、升级、启停

## 12.2 日志规范

日志至少应具备以下上下文：

- `traceId`
- `requestId`
- `tenantId`
- `userId`
- 接口路径
- 耗时
- 结果状态

## 12.3 异常规范

- 统一使用全局异常处理。
- 业务异常返回标准业务码。
- 技术异常要记录日志，但不能直接把堆栈原样返回前端。
- 对用户可见的错误信息要可理解、可定位。

## 12.4 敏感信息规范

日志、异常、审计中不得直接暴露：

- 密码
- 完整 Token
- 私钥
- 完整身份证号
- 完整手机号
- 支付密钥

## 13. 配置与安全规范

## 13.1 配置分层

配置分为：

- 环境配置
- 平台配置
- 租户配置

不同作用域必须分开治理，不能混在一个“万能配置表”语义里失控扩张。

## 13.2 敏感配置

- 敏感配置必须支持加密存储。
- 敏感配置读取与修改必须有审计。
- 接口返回敏感配置时优先返回“已配置”标识或脱敏值。

## 13.3 安全默认值

- 所有外部调用都应有超时。
- 所有写接口都应有基础防重复提交能力或幂等策略。
- 高风险接口要考虑二次验证、验证码、来源校验或更强审计。

## 14. 测试规范

## 14.1 单元测试与集成测试

以下变更优先补测试：

- 权限判断
- 登录与认证流程
- 数据权限与租户边界
- 复杂应用服务
- 关键 Mapper SQL
- 文件与消息主链路

## 14.2 测试命名

测试类和测试方法要能说明场景，不使用无语义命名。

## 14.3 回归要求

修改以下内容时必须重点回归：

- 公共安全模块
- 公共 Web 层
- 公共响应结构
- 权限快照逻辑
- 租户上下文逻辑
- outbox 投递逻辑

## 15. 后端开发红线

1. 禁止 Controller 直接操作 Mapper 完成复杂业务。
2. 禁止跨模块直接读写别的模块私有表实现功能。
3. 禁止绕开统一安全体系自行实现会话和鉴权。
4. 禁止租户级数据查询不带租户边界。
5. 禁止写接口没有审计或最少日志留痕。
6. 禁止对外部依赖不设超时和失败策略。
7. 禁止把异常堆栈直接返回前端。
8. 禁止把导入导出、批处理全部做成同步阻塞接口。
9. 禁止把敏感配置明文返回前端。
10. 禁止新增公共能力时直接复制粘贴旧实现而不沉淀到 `libs/*`。

## 16. 推荐开发流程

新增后端能力建议按以下顺序推进：

1. 明确归属模块
2. 设计 DTO、VO、Entity 和接口契约
3. 设计 SQL、索引与审计点
4. 实现应用服务与数据访问
5. 接入权限、租户、缓存、日志、异常
6. 补充测试与迁移脚本

这样做可以避免功能先跑起来，后面再为边界、审计和一致性返工。
