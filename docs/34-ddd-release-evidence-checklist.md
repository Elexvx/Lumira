# DDD Release Evidence Checklist

本清单用于把“全域 DDD + 高性能架构升级方案”的完成条件落到可执行证据。发布前以 `DDD_RELEASE_EVIDENCE_STRICT=true node scripts/ddd-release-evidence-gate.mjs` 为最终汇总门禁；没有真实环境证据时，只能视为代码级完成，不能视为发布完成。

Orchestrator preflight 是固定发布契约的一部分，当前必须包含 11 项：`release-provenance`、`release-config-env-file`、`backend-runtime-base-url`、`ai-runtime-base-url`、`frontend-runtime-base-url`、`frontend-deployed-expectation`、`docker-cli`、`docker-daemon`、`ai-provider-remote-expectation`、`ai-owner-gateway-remote-expectation`、`migration-runtime-evidence`。共享 orchestrator contract 会校验这些 check ID 存在且不重复、不出现未知项，`blockers/warnings` 计数与明细一致、`status` 与是否存在 blocker 一致，并要求每项带有可读 `detail` 和对应 `envKeys`；任何漂移都会进入 strict release gate。

Frontend smoke evidence 会输出 `flowCoverage`，逐条标记必需 flow 的 `passed`/`missing` 状态、匹配到的 Playwright 标题，以及缺失原因。artifact 还会写入 `diagnostics.playwrightReport` 与 `diagnostics.staticSpecCoverage`，用于区分“Playwright JSON 未生成/未上传”和“required flow 没有写入 `@smoke` spec”。contract 会要求动态 flow 覆盖和静态 spec 覆盖都与 required-flow 清单精确同步。Playwright JSON 缺失、测试未运行或某个 flow 没有 passed `@smoke` 用例时，strict gate 仍会阻断发布，但发布负责人可以直接从 `flowCoverage` 和静态覆盖诊断定位缺口。

运行时证据统一要求：发布流水线生成 readiness、release config、authenticated performance、File、Payment、Outbox、Job、AI 和 Frontend smoke artifact 时，应设置 `DDD_EVIDENCE_ENVIRONMENT`、`DDD_RELEASE_CANDIDATE`、`DDD_EVIDENCE_OPERATOR`。strict 模式下这些 smoke/evidence 脚本会在生成阶段拒绝缺失或占位 provenance；strict release gate 也会再次要求 runtime artifact 具备非占位 `sourceEnvironment`、`releaseCandidate`、`evidenceOperator`，防止证据无法追溯到环境、版本和执行人。Readiness、Authenticated performance、File、Payment、Job、AI 和 Frontend 运行证据会写入 `productionEquivalence`：本地 HTTP artifact 可以保留为开发调试证据，但 strict 发布必须使用 HTTPS 且非 localhost 的准生产/生产等价 baseURL，并在需要时通过 owner-specific `DDD_*_DEPLOYMENT_EVIDENCE` 或通用部署证据变量附加部署/变更单/日志引用。

对于已经存在但缺 provenance 的历史 runtime artifact，可用 `DDD_RUNTIME_PROVENANCE_BACKFILL=true DDD_EVIDENCE_ENVIRONMENT=... DDD_RELEASE_CANDIDATE=... DDD_EVIDENCE_OPERATOR=... node scripts/ddd-backfill-runtime-provenance.mjs` 进行 metadata-only 补录。对于缺结构化 `productionEquivalence` 的旧 artifact，可用 `DDD_RUNTIME_PRODUCTION_EQUIVALENCE_BACKFILL=true node scripts/ddd-backfill-runtime-provenance.mjs` 基于 `baseUrl` 保守补录。该工具只补来源字段、production-equivalence 元数据和 backfill 审计字段，不改变证据状态、失败列表或性能结果；它不会解除 localhost、HTTPS、生产等价环境或新鲜度 blocker。

证据新鲜度统一要求：strict release gate 默认要求关键 artifact 的 `generatedAt`、`checkedAt`、`finishedAt` 或 `startedAt` 距离执行门禁不超过 24 小时，EXPLAIN JSON 以文件 mtime 校验。可用 `DDD_RELEASE_MAX_ARTIFACT_AGE_HOURS` 调整窗口；authenticated performance baseline 是已验收历史基线，不参与 freshness 校验。

## 3. 发布判定

- `node scripts/ddd-release-evidence-gate.mjs`：本地 advisory，只汇总缺口，不代表可发布；readiness summary 会显示 `Release gate mode: advisory`，若仍有 blocker 则状态是 `NOT_READY`，只有 gate 存在且 blocker/contract issue 均为 0 时才会标记为 `ADVISORY`。
- `DDD_RELEASE_EVIDENCE_STRICT=true node scripts/ddd-release-evidence-gate.mjs`：准生产/发布流水线阻断门禁；缺失 orchestrator run 报告、orchestrator preflight `BLOCKER`、缺失后端构建/测试证据、缺失 Docker 镜像构建证据、缺失前端构建/测试证据、缺失 Flyway 新库/旧库运行验证、缺失生产等价配置矩阵、缺失 checksum manifest、localhost-only 运行时 artifact、运行时 artifact 缺少来源元数据、前端 smoke 未声明部署环境或 baseURL 非 HTTPS、artifact 超过 freshness 窗口、缺失性能 baseline、baseline 来源为 localhost 或缺少验收元数据、超过 10% 性能回退或缺失回滚演练证据都会被视为不合格证据。gate 产物自身也会通过共享 contract 复核 `summary` 与 `checks[]`、`blockers[]`、`warnings[]` 明细一致，拒绝非法 check 状态或缺少 name/detail 的条目。
- strict 通过后仍需保留部署版本、数据库 migration 版本、配置版本、回滚窗口和相关日志索引，作为变更审计的一部分。

secret 的情况下列出当前 ready batch，并支持同一组 `DDD_RELEASE_BATCH`、`DDD_RELEASE_OWNER`、`DDD_RELEASE_PRIORITY` 过滤器先预览执行范围；正式执行时会检查 `DDD_RELEASE_ENV_FILE` 已设置、文件存在且不是 `release-env-missing.template.env`，然后用 safe dotenv loader 加载真实发布配置；该 loader 只接受 `KEY=value` 或 `export KEY=value`，不会执行 env 文件中的 shell 语句；设置 `DDD_RELEASE_BATCH=<batch-id>` 可以只执行一个 ready batch，设置 `DDD_RELEASE_OWNER=<owner>` 可以只执行该 owner 当前 ready batch，设置 `DDD_RELEASE_PRIORITY=P0|P1|P2|P3` 可以只执行该优先级当前 ready batch，多条件组合时必须同时匹配，未匹配会失败；设置 `DDD_RELEASE_DRY_RUN=1` 可预览命令但不会生成证据；设置 `DDD_RELEASE_CHECK_ENV_ONLY=1` 可只运行 env group 预检并跳过证据命令，适合发布负责人先确认 GitHub environment secret 或 `.env.release` 注入完整性；缺少任何 env group 默认会失败，只有显式设置 `DDD_RELEASE_ALLOW_MISSING_ENV=1` 才会继续，这个开关只用于本地诊断，不能用于正式上线。env group 预检使用 release config contract 的别名组，例如 `LUMIRA_BASE_URL=DEPLOY_CHECK_BASE_URL|LUMIRA_BASE_URL`、`DB_USERNAME=DB_USERNAME|MYSQL_USER|SPRING_DATASOURCE_USERNAME`，组内任意 key 存在就视为该组覆盖。该脚本只生成命令提示，不写 secret，不作为发布证据。`artifacts/ddd/release/release-action-dependency-graph.json` 和 `.md` 会从同一批次数据生成 `nodes`、`edges`、`readyBatchIds`、`blockedBatchIds`、`byPriority`、`executionLevels`、`graphDensity` 和 `compressedEdges`，每个 node 也携带同批次 `envKeys` 和 `envCheckGroups`；Markdown 先显示按 priority 聚合的压缩 Mermaid 图，再显示完整 DAG，适合先分派可并行 P0 工单并识别仍被依赖阻塞的 P1/P2/P3 工单。`commands` 由固定 source/owner 证据流程和行动项里的命令共同生成，确保 authenticated performance、frontend smoke、manifest、orchestrator 等批次不会漏掉前置采集命令。`expectedArtifacts` 是执行后应归档或刷新的最小证据集合，并按 owner 精确到产物，例如 File/Job/Payment business E2E owner 分别只要求自己的 E2E artifact；manifest 批次还会列出实际缺失 artifact 本身，authenticated runtime baseline 缺失时会同时要求 baseline 和 promotion audit。`exitCriteria` 是进入下一批前的人工验收门槛，不能只看命令退出码。

`release-owner-input-receipt.json`、`.csv`、`-items.csv`、`-items.md` 和 `.md` 会把 owner input collection 的当前验收状态输出成脱敏回执；`.csv` 一行一个 owner，`-items.csv` 一行一个 canonical key，`-items.md` 是同一逐项清单的 Markdown checklist，便于导入工单或表格逐项关闭 34 个输入；`release-owner-input-receipt-items/` 目录会再按 owner 拆出逐负责人 checklist，适合直接分派给 platform-events、platform-owners、release-infra、ai-owner 和 payment-owner。所有回执只包含 owner、key 名、alias、输入数量、remaining placeholders/missing、packet/handoff 相对路径和 pass criteria，不包含 secret 或真实 env 值。

`release-next-action-queue.json`、`.csv` 和 `.md` 也会展示 owner input receipt 的 `PASS/PENDING_OWNER_INPUT`、pending owner、missing criteria、required owner input 数和逐 owner checklist 路径；contract 会要求这些字段自洽，并要求 `cutoverAllowed=true` 时 receipt 必须 `PASS` 且 `cutoverReady=true`。它只用于分派和排障，不是 waiver。

`release-blocker-closure-plan.json`、`.csv` 和 `.md` 也会展示同一份 owner input receipt 摘要，包含 pending owner、missing criteria 和 required owner input 数；readiness summary contract 会要求 closure plan 与 next-action queue 的 receipt 一致。它只帮助 owner 分派和关闭 blocker，不允许绕过 final go/no-go。

`release-next-action-commands.sh` 的 dry-run、list 和 detail 模式不需要 secret；设置 `DDD_RELEASE_NEXT_ACTION_CHECK_ENV=1` 时只用 safe dotenv loader 读取真实 `DDD_RELEASE_ENV_FILE` 并检查当前 RUN_NOW 项缺少哪些 key，不执行证据命令、不输出 secret 值。正式执行时必须设置 `DDD_RELEASE_NEXT_ACTION_EXECUTE=1` 且提供真实 `DDD_RELEASE_ENV_FILE`。脚本会拒绝缺失文件和 `release-env-missing.template.env`，再用同一 safe dotenv loader 解析 env 文件执行队列命令；该 loader 只接受 `KEY=value` 或 `export KEY=value`，不会执行 env 文件中的 shell 语句。批量诊断时可显式加 `DDD_RELEASE_NEXT_ACTION_CONTINUE_ON_ERROR=1` 继续执行后续命令；只要任一命令失败，最终仍会非零退出，不能作为上线成功依据。

`release-blocker-closure-commands.sh` 是 blocker closure plan 的命令入口，默认只列 `RUN_NOW_LOCAL` 和 `RUN_NOW_WITH_REAL_ENV` 项，不执行。可用 `DDD_RELEASE_CLOSURE_DETAIL=1` 查看单项详情，用 `DDD_RELEASE_CLOSURE_CHECK_ENV=1` 只检查所需 key，用 `DDD_RELEASE_CLOSURE_EXECUTE=1` 执行；支持 `DDD_RELEASE_CLOSURE_ORDER`、`DDD_RELEASE_CLOSURE_OWNER`、`DDD_RELEASE_CLOSURE_PRIORITY`、`DDD_RELEASE_CLOSURE_KIND` 过滤。env-check 和 execute 都必须提供真实 `DDD_RELEASE_ENV_FILE`，并拒绝模板文件；脚本只打印 key 名，不打印 secret 值。批量诊断时可显式加 `DDD_RELEASE_CLOSURE_CONTINUE_ON_ERROR=1` 继续执行后续命令；只要任一命令失败，最终仍会非零退出。

`release-execution-commands.sh` 和 `release-final-owner-queue-commands.sh` 的 continue-on-error 开关分别是 `DDD_RELEASE_CONTINUE_ON_ERROR=1` 与 `DDD_FINAL_OWNER_QUEUE_CONTINUE_ON_ERROR=1`。它们只用于快速收集完整失败面；脚本会累计失败并在结尾非零退出，不能替代 strict gate、manifest、性能、迁移、回滚或生产等价证据。

`release-execution-commands.sh` 真实执行模式会生成 `release-execution-run-report.json`，记录 batch/owner/priority 过滤条件、整体退出码、`summary.totalEntries/succeededEntries/failedEntries` 汇总计数，以及每条命令的 `batchId`、`owner`、`priority`、退出状态、耗时和完成时间；可用 `DDD_RELEASE_EXECUTION_REPORT` 指定其他安全路径。dry-run 和 env-check-only 不写该报告，避免把预演误当成真实执行证据。脚本写出报告后会自动调用 `node scripts/ddd-release-execution-run-report-contract.mjs` 校验 schema、`PASS/FAIL` 与退出码一致性、summary 计数与 entries 明细一致性，并拒绝命令里出现未脱敏 secret、release env 文件路径或本机仓库绝对路径。`node scripts/ddd-release-execution-run-report-summary.mjs` 可把该报告追加到 GitHub Step Summary 或输出 Markdown，方便发布负责人按 batch/owner/priority 快速定位失败命令。该报告用于排障、审计和 owner 复盘，不替代任何 expected artifact、strict release gate 或 final go/no-go。

`release-closure-wave-env-matrix.json`、`.csv` 和 `.md` 会按 closure wave 汇总 owner、batch、env keys、命令和预期证据；`release-closure-wave-env.template.env` 是按 wave 分段的安全模板，只放 key 和 `__REQUIRED__` 占位符，不放 secret 值。真实环境执行前先按该模板补齐 `.env.release`，再用 `DDD_RELEASE_CLOSURE_CHECK_ENV=1` 预检。

`release-closure-wave-receipts.json`、`.csv` 和 `.md` 会按 wave 检查 expected artifacts 是否已经落盘，并标出 `ARTIFACT_MISSING`、`CONTENT_BLOCKED` 或 `READY_FOR_STRICT_GATE_RERUN`；`CONTENT_BLOCKED` 表示 artifact 已存在但 provenance、baseline 或内容合同仍未满足，`blockerHints` 会保留具体原因且不会被误列为缺失文件路径。每个 wave 都带 `node scripts/ddd-release-evidence-gate.mjs` 和 `node scripts/ddd-release-readiness-summary.mjs` 复核命令。它只帮助执行后验收，不替代 strict gate。`release-final-go-no-go.*` 和 `release-final-owner-queue.*` 会继续透传 content blockers，方便 CI 日志和 owner 分派直接定位内容问题。

`release-closure-wave-blocker-map.json`、`.csv` 和 `.md` 会把 closure wave 与 priority action、source-derived category、候选 blocker hint、命令和预期证据关联起来。该映射用于执行后解释 gate 变化，不是 waiver；只有重新运行 strict release gate 且 blocker 实际消失，才算关闭。

`release-performance-baseline-closure.json` 和 `.md` 专门收敛 authenticated performance baseline：它会列出当前 actual、baseline promotion、baseline 缺口、不能晋级的 blocker、所需 env keys 和推荐命令。baseline 只能从生产等价、非本地、无失败的 actual 晋级，不能手工伪造。

`release-performance-baseline-commands.sh` 是同一闭环的安全执行入口：默认输出 detail/dry-run，`DDD_AUTH_PERF_BASELINE_CHECK_ENV=1` 只检查 env key，`DDD_AUTH_PERF_BASELINE_EXECUTE=1` 才执行性能采集、baseline 晋级、manifest、release gate 和 readiness summary。它必须使用真实 `DDD_RELEASE_ENV_FILE`，拒绝生成模板 env 文件，并要求真实 env 文件权限收紧到 `600`。

`release-final-go-no-go.json`、`.csv` 和 `.md` 会把 strict gate、fast-track、closure wave 回执、closure blocker map 和性能 baseline closure 汇总成最终发布包；JSON 和 CSV 都同时输出 `recommendation` 与兼容字段 `finalRecommendation`。发布切流只看 `cutoverAllowed=true`，且该字段只能由 strict gate 0 blocker、cutover 全 PASS、wave 回执全 ready、性能 baseline READY 共同推出；任何 stop reason 都必须回到对应 owner 证据修复，不能人工改文件放行。

`release-final-go-no-go-gate.sh` 会读取同一 final packet。默认模式用于人工查看；CI/CD 切流步骤必须设置 `DDD_FINAL_GO_NO_GO_ENFORCE=1`，NO-GO 时脚本以退出码 10 失败，GO 时退出 0。该脚本只消费已生成证据，不会自动补证据或绕过 strict gate。

final packet 的 `ciSummary` 会固定输出 `enforceCommand`、`nonGoExitCode=10`、`stopOwners`、`blockedArtifactPaths`、`firstNextCommand` 和 rerun 命令。发布失败时先看 `stopOwners` 分派 owner，再看 `blockedArtifactPaths` 确认缺失证据，最后执行 `firstNextCommand` 或对应 owner wave 命令。

`release-final-owner-queue.json`、`.csv` 和 `.md` 会把 final go/no-go 的 stop owners 进一步展开成 owner 级工单队列：每个 owner 包含稳定 `queueOrder`、`canExecute`、命令/env/artifact/stop reason 计数、cutover item、ready/blocked batch、closure wave、缺失 artifact、首条命令和 rerun 命令。队列顶层还会展示 owner input receipt 的 `PASS/PENDING_OWNER_INPUT`、pending owner 数、missing criteria、required owner input 数和逐 owner checklist 路径；`cutoverAllowed=true` 时该 receipt 必须为 `PASS` 且 `cutoverReady=true`。CI 失败后优先把该 CSV 或对应 checklist 导入工单系统，按 `queueOrder` 和 `canExecute=true` 分派，owner 完成证据后再重跑 final gate。

`release-final-owner-queue-commands.sh` 是同一 owner queue 的安全执行入口。默认只列 `ACTIONABLE` owner；可用 `DDD_FINAL_OWNER_QUEUE_OWNER=<owner>`、`DDD_FINAL_OWNER_QUEUE_STATUS=ACTIONABLE|WAITING` 和 `DDD_FINAL_OWNER_QUEUE_DETAIL=1` 查看单 owner 明细；设置 `DDD_FINAL_OWNER_QUEUE_CHECK_ENV=1` 时只静态解析真实 `DDD_RELEASE_ENV_FILE` 并检查该 owner 所需 env key，不 `source` 文件、不执行证据命令；`WAITING` owner 允许 detail/check env 提前准备，但 `DDD_FINAL_OWNER_QUEUE_EXECUTE=1` 会拒绝执行，必须先关闭依赖 blocker；真实 env 文件权限必须是 `600`，否则 check/execute 都会拒绝继续；只有设置 `DDD_FINAL_OWNER_QUEUE_EXECUTE=1` 才加载 env 并执行命令。执行后仍必须重跑 strict gate、readiness summary 和 final go/no-go gate。

执行模式会生成 `release-final-owner-queue-run-report.json`，记录 owner/status 过滤条件、整体退出码、`summary.totalEntries/succeededEntries/failedEntries` 汇总计数，以及每条命令的 `commandIndex/commandCount`、退出状态和耗时；可用 `DDD_FINAL_OWNER_QUEUE_REPORT` 指定其他安全路径。该报告是排障和审计辅助，不替代各 evidence artifact 或 strict gate。

执行脚本写出报告后会自动调用 `node scripts/ddd-final-owner-queue-run-report-contract.mjs` 校验 run report 的 schema、`PASS/FAIL` 与退出码一致性、`summary` 计数与 `entries` 明细一致性，以及每条命令 entry 的 owner、queueOrder、queueStatus、commandIndex、commandCount、command、status、duration 和 finishedAt；该脚本也可单独复核历史报告。`queueOrder/queueStatus` 用于追溯该命令为什么属于当前执行批次，`commandIndex/commandCount` 用于定位 owner 内第几条命令失败，防止 owner 回执脱离 final queue 上下文。该检查只验证审计报告可消费，不作为发布放行证据。

`release-final-owner-queue-env.template.env` 会按 owner 分段列出 final owner queue 所需 env key，值统一为 `__REQUIRED__`，不会包含 secret；每个 owner 段也会标注 `queueOrder` 和 `canExecute`，方便 secret 填写人先处理当前可执行 owner。执行人可按该模板补齐安全位置中的 `.env.release`，再用 `DDD_FINAL_OWNER_QUEUE_CHECK_ENV=1` 预检单个 owner。

`release-final-owner-queue-env-init.sh` 可从模板初始化本地真实 env 文件，默认写入 `.env.release.local` 或 `DDD_RELEASE_ENV_FILE`，权限固定为 `600`，并默认拒绝覆盖已有文件；初始化成功后的下一步提示会指向当前 `queueOrder` 最靠前且 `canExecute=true` 的 owner，而不是固定 owner。不要把初始化后填入真实值的文件提交到仓库。

`scripts/ddd-release-config-sync.test.mjs` 会校验 `releaseConfigGroups` 中的必填项在 `docs/36-ddd-release-env-template.env` 和 `.github/workflows/ddd-release-evidence.yml` 中都有至少一个对应变量，并校验 workflow 的配置预检位于前端依赖安装和 Docker setup 之前，避免新增发布配置要求时漏同步 CI secret 或模板。`release-config-evidence.json` 还会输出 `coverageMatrix`，按 check 展示 runtime、env file、template 和 workflow 四层覆盖；readiness summary 会显示 required/runtimePresent/envFile/template/workflow 覆盖计数，帮助区分“发布模板已覆盖但本次运行没有注入 env”和“模板或 workflow 漏键”。

`scripts/ddd-dockerfile-contract.test.mjs` 会在不依赖 Docker daemon 的情况下静态校验 `deploy/docker/service.Dockerfile` 和 `deploy/docker/frontend.Dockerfile`：server 镜像必须保留 `SERVICE_MODULE`/`SERVICE_DIR`、非 root `USER`、`8080` 暴露和 entrypoint，frontend 镜像必须使用 frozen pnpm lockfile、执行生产构建、安装生产 nginx 配置并暴露 `80`。它不能替代真正的 Docker build/inspect 证据，但能在 CI 早期阻止 Dockerfile 发布契约漂移。

`scripts/ddd-rollback-drill-sync.test.mjs` 会校验 `docs/35-ddd-rollback-drill-template.json`、`scripts/ddd-init-rollback-drill.mjs` 和 rollback deferral owner handoff 都覆盖共享 contract 中的十个 bounded context，避免新增或重命名上下文后 rollback drill 模板、初始化草稿、owner 分派文件和 release gate 漂移。

`scripts/ddd-rollback-drill-evidence.mjs` 会在校验已有 rollback draft 时，用 `DDD_EVIDENCE_ENVIRONMENT`、`DDD_RELEASE_CANDIDATE`、`DDD_EVIDENCE_OPERATOR` 补齐缺失的 artifact metadata；这只消除来源元数据缺口，不会把 `TODO` 上下文改成通过。`DDD_ROLLBACK_DRILL_CHECK_ENV=true` 只生成 `rollback-drill-handoff.md` 或 `DDD_ROLLBACK_DRILL_HANDOFF_FILE` 指定的交接文件，不会写回主 rollback artifact，也不会替代真实 PASS/DEFERRED 证据。确实需要批量延期时，可先运行 `scripts/ddd-rollback-deferral-template.mjs` 生成覆盖十个 bounded context 的 deferral 输入模板，再通过 `DDD_ROLLBACK_DRILL_DEFERRAL_FILE` 提供已审批文件，其中每个上下文都必须带真实 `notExercisableReason`、`riskAcceptedBy`、`deferralEvidence` 和未来 `expiresAt`；脚本会把已应用的上下文写入 `appliedDeferrals`、`contextDiagnostics[].deferralApplied` 和机器校验的 `summary`。共享 contract 会校验 `summary.requiredContexts/contexts/passContexts/deferredContexts/readyContexts/missingRequiredContexts/unknownContexts/duplicateContexts/diagnostics/appliedDeferrals/blockers/warnings` 与明细一致。readiness summary 的 rollback action 会输出结构化 `reason`，明确每个上下文是缺 PASS 演练证据还是缺已审批 DEFERRED 风险接受，避免 release priority 中出现无法执行的空原因。`scripts/ddd-rollback-deferral-template.test.mjs`、`scripts/ddd-rollback-drill-sync.test.mjs` 和 `scripts/ddd-rollback-drill-evidence.test.mjs` 覆盖该行为，确保真实 PASS/DEFERRED 演练证据仍是 strict 发布门槛。
