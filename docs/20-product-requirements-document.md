## 2. 项目背景

随着企业数字化系统不断增多，后台管理系统往往面临用户体系重复建设、权限模型不统一、文件与消息能力分散、系统配置难以审计、AI 能力难以接入生产流程、插件扩展缺少治理等问题。传统后台模板通常只能满足基础页面搭建，难以支撑长期运营、多人协作、模块扩展、安全治理和准生产部署。

Lumira 项目定位为企业级 SaaS 智能应用平台底座。项目以 React、TypeScript、Umi Max、Ant Design、Java 21、Spring Boot、MySQL、Redis、Docker 等技术为基础，提供认证、权限、系统管理、AI 助手、知识库、文件中心、消息中心、插件中心、国际化、支付配置、审计监控和容器化部署等能力。

当前项目已经从早期“多进程微服务”收敛为“单体微服务”运行模式：生产和本地默认只启动 `services/lumira-server` 一个后端入口，由它聚合系统、认证、文件、消息、插件、本地化、支付和任务能力；代码仍按 `services/*-service` 和 `libs/*` 保留模块边界，为后续物理拆分预留条件。

## 3. 产品定位

本产品不是单一业务系统，而是一套可复用、可扩展、可交付的企业级 SaaS 管理平台底座。它面向需要快速构建内部管理系统、AI 应用后台、插件化业务平台、企业数字化工作台的团队，提供统一的基础能力和管理入口。

产品核心定位如下：

| 定位 | 说明 |
| --- | --- |
| 企业级管理底座 | 提供用户、角色、菜单、权限、字典、配置、审计、监控等通用后台能力 |
| 智能应用工作台 | 提供 AI 助手、AI 员工、知识库、模型服务、工具调用和对话分享能力 |
| 可扩展平台 | 支持插件上传、安装、升级、回滚、启停和运行时访问 |
| 多端适配管理后台 | 支持桌面端为主、兼顾平板和移动端关键操作的响应式管理界面 |
| 准生产部署方案 | 前端支持 Vercel 托管，后端支持 Docker 容器化、Nginx API 代理、健康检查、备份恢复和可观测性 |

## 4. 建设目标

### 4.1 业务目标

1. 建设一套统一的企业级 SaaS 管理平台，减少后续业务系统重复开发成本。
2. 打通用户、角色、菜单、权限、审计、文件、消息、配置等基础后台主链路。
3. 内置 AI 助手和知识库能力，使平台具备智能问答、知识检索和工具调用基础。
4. 提供插件机制，使后续业务模块可以以插件或模块方式扩展。
5. 提供完整部署、运维、监控和回滚能力，使系统能够支撑真实演示和准生产运行。

### 4.2 产品目标

1. 用户登录后能够根据权限进入对应工作台和管理页面。
2. 管理员能够维护用户、角色、菜单、部门、字典、系统配置、个性化配置和安全配置。
3. 管理员能够查看系统监控、审计日志、在线用户和接口文档。
4. 普通用户能够使用个人中心、我的文件、下载中心、消息通知和 AI 助手。
5. AI 管理人员能够配置 AI 员工、模型服务、知识库和工具策略。
6. 平台运营人员能够管理插件、国际化词条、支付服务商配置和通知渠道配置。
7. 平台配置人员能够维护资料字段、品牌视觉、水印、浮窗、协议文案和平台更新检查策略。

### 4.3 技术目标

1. 保持前后端分离架构，统一 API 响应、请求封装、错误处理和鉴权方式。
2. 后端以 `lumira-server` 为统一运行入口，保留模块化边界和未来拆分可能。
3. 支持 MySQL 持久化、Redis 会话与缓存、Flyway 数据迁移。
4. 支持 Docker Compose 部署、生产环境变量隔离、API 代理、健康检查和轻量压测。
5. 支持 Prometheus、Grafana、Loki、Tempo、OpenTelemetry 等可观测性能力按需启用。

### 4.4 底座建设目标

1. 统一前后端技术底座，便于后续快速复制业务模块。
2. 实现贯穿认证、授权、数据、缓存、文件、日志、任务、消息、限流和运维链路的平台能力。
3. 支持桌面端为主、兼顾平板端和移动端关键操作路径的交互体验。
4. 具备高可靠架构，能够应对流量波动、单点故障、弱依赖异常、发布失误和缓存/数据库压力。
5. 具备可观测、可审计、可回滚、可恢复的工程体系。

## 5. 产品架构原则

### 5.1 总体技术路线

| 维度 | 方案 |
| --- | --- |
| 前端 | React、TypeScript、Umi Max、Ant Design、Ant Design Pro、ProComponents |
| 后端 | Java 21、Spring Boot、Spring Security、MyBatis Plus、Redis、MySQL、Flyway |
| 架构 | 前后端分离、模块化单体优先、保留微服务拆分边界、云原生部署预留 |
| 部署 | Vercel 托管前端，Docker Compose 承载后端聚合服务与基础组件 |

### 5.2 架构分层

系统采用“五层一横切”的平台设计思路：

1. 多端接入层：浏览器、移动端、第三方入口、插件运行时入口。
2. 前端应用层：管理后台、AI 助手、个人中心、系统设置等页面能力。
3. 网关与接入层：API Proxy、鉴权入口、静态资源分发、WebSocket 入口。
4. 业务服务层：认证、系统、文件、消息、插件、本地化、支付、AI、任务等服务模块。
5. 数据与基础设施层：MySQL、Redis、文件存储、日志、监控、备份恢复等能力。
6. 横切能力层：统一覆盖租户、认证授权、审计、限流、异常、缓存、配置、可观测和灰度发布能力。

### 5.3 前端规范

#### 5.3.1 前端目标

1. 建立稳定的壳层，保证系统页面扩展时不需要重复发明布局和交互规则。
2. 建立统一页面骨架，保证列表页、表单页、配置页、详情页的体验一致。
3. 建立统一响应式策略，使桌面端、平板端、移动端都具有明确降级方案。
4. 建立统一权限接入方式，避免页面各自散写权限判断。
5. 建立统一状态与数据流规范，减少页面层重复维护请求、缓存和会话逻辑。

#### 5.3.2 前端分层规范

前端按三层组织：

1. 壳层：主布局、导航、顶部工具区、标签页、用户入口、通知入口、异常页。
2. 基础能力层：请求封装、认证、权限快照、租户上下文、缓存、hooks、工具、类型、组件。
3. 业务页面层：只承载业务页面，不重复实现基础壳层和基础能力。

目录职责建议如下：

| 目录 | 职责 |
| --- | --- |
| `layouts/` | 壳层布局、侧边导航、顶部区、配置页布局、AI 页面布局 |
| `pages/` | 业务页面、配置页面、异常页、登录页 |
| `components/` | 可复用展示组件和交互组件 |
| `services/` | 按域划分的接口调用封装 |
| `auth/` | 登录态、会话恢复、权限快照、登录跳转、Passkey 流程 |
| `hooks/` | 复用逻辑和页面行为抽象 |
| `theme/` | 主题 token、反馈桥接、间距规范 |
| `types/` | 接口模型、领域类型、公共类型 |
| `plugins/` | 插件运行时装载和前端清单处理 |
| `cache/` | 本地缓存、跨页面状态和租户维度缓存策略 |

#### 5.3.3 布局与壳层规范

1. 主布局统一采用左侧导航、顶部工具区、主内容区。
2. 配置类页面统一采用设置页布局，不允许每页自建设置外壳。
3. AI 页面使用独立 AI 布局，突出会话区、消息区、输入区和工具反馈区。
4. 用户布局只用于登录、认证、找回密码、激活等独立流程。
5. 空白布局用于嵌入页、全屏页、插件页或不应展示主导航的流程页。

内容区统一提供：

1. 页面标题和面包屑。
2. 页面级主操作入口。
3. 滚动承载区。
4. 加载态、空态、异常态统一承载能力。

#### 5.3.4 路由与菜单规范

1. 路由按业务域组织，而不是按技术类型组织。
2. 菜单优先基于后端权限快照和菜单树动态生成。
3. 页面存在不代表可访问，必须经过权限判断。
4. 无权限访问统一进入 403，无匹配路由统一进入 404。
5. 默认首页统一从用户默认首页或系统首页策略中解析。
6. 插件菜单与本地菜单必须走同一套菜单拼装和权限裁剪逻辑。

#### 5.3.5 页面骨架规范

列表页统一采用：

1. 页面头。
2. 查询区。
3. 操作区。
4. 表格区或卡片区。
5. 抽屉详情区或详情页入口。

表单页统一区分：

1. 新增。
2. 编辑。
3. 只读查看。

详情页统一优先包含：

1. 基础信息区。
2. 状态区。
3. 关联信息区。
4. 日志记录区。

配置页统一优先采用：

1. 左侧分类导航 + 右侧内容区。
2. 或顶部 Tab + 主编辑区。

#### 5.3.6 查询区与表格区规范

1. 查询区只承载筛选，不承载主操作。
2. 常用筛选条件前置，低频条件折叠。
3. 默认避免每输入一个字符就触发请求。
4. 表格列顺序统一优先主信息、状态、时间、操作。
5. 表格必须支持空数据、加载中、错误提示和分页状态。
6. 列表页默认通过统一管理页组件承载，不鼓励业务页直接手写整套表格外壳。

#### 5.3.7 详情、弹窗与抽屉规范

1. 列表内详情和轻编辑优先使用抽屉。
2. 复杂表单和复杂详情优先使用独立页面，不强塞弹窗。
3. 轻量确认使用 Modal。
4. 移动端抽屉和弹窗统一退化为更适合触控的全屏层。
5. 抽屉主操作统一优先放在右上角 `extra` 区域，长流程才使用 footer。

#### 5.3.8 响应式规范

响应式不是简单缩放，而是结构重组：

1. 桌面端保留完整能力和高密度信息。
2. 平板端保留核心能力并降低信息密度。
3. 移动端只保留关键高频能力，列表退化为卡片流，查询区默认折叠。

具体要求：

1. 桌面端适合复杂表格、批量操作、树结构。
2. 平板端减少低频列，查询区压缩为两列。
3. 移动端不直接搬运超宽表格，操作按钮应收纳为动作区或更多菜单。

#### 5.3.9 组件复用规范

应沉淀系统级组件：

1. 页面容器。
2. 查询区。
3. 操作栏。
4. 表格容器。
5. 详情抽屉。
6. 状态标签。
7. 权限按钮。
8. 文件上传。
9. 空态、异常态、加载态组件。

管理页交互统一要求：

1. 后台管理页优先使用统一 `ManagementPage`、`ManagementTable`、`ManagementDrawer`、`TableActionBar` 组合。
2. 多 Tab 管理页统一使用页面级 Tabs。
3. 行操作统一通过 `TableActionBar` 或同等级收纳菜单处理。

#### 5.3.10 权限、租户与状态管理规范

1. 菜单裁剪基于权限快照统一完成。
2. 按钮显隐通过统一权限组件或 hook 完成。
3. 页面访问控制在路由层处理，不在业务组件层零散处理。
4. 租户切换后必须刷新菜单、权限快照、字典缓存和配置缓存。
5. 缓存必须带租户维度，禁止租户切换后保留旧租户页面状态。
6. 全局状态只保留用户信息、当前租户、权限快照、通知数、主题等公共状态。
7. 页面状态由页面自身管理，避免无边界上升为全局状态。

#### 5.3.11 请求、缓存与错误处理规范

请求层统一处理：

1. Token 注入。
2. 登录失效跳转。
3. 错误码拦截。
4. 文件流处理。
5. 分页参数映射。
6. SSE 流式接口处理。
7. 插件运行时异常兜底。

缓存与页面保活规则：

1. 高频切换列表页、配置页可缓存。
2. 高敏感表单、一次性流程页、强实时页面不默认缓存。
3. 缓存必须明确是否允许跨标签、跨租户、跨会话。

#### 5.3.12 前端开发红线

1. 不允许每个页面自建一套布局骨架。
2. 不允许页面中散写接口请求逻辑和权限判断字符串。
3. 不允许使用 `window.innerWidth` 作为响应式主策略。
4. 不允许移动端直接照搬桌面端超宽表格。
5. 不允许租户切换后保留旧租户缓存和页面状态。
6. 不允许把前端显隐当作真正的安全边界。

### 5.4 后端规范

#### 5.4.1 后端目标

1. 建立清晰的模块化底座。
2. 建立稳定的多租户上下文机制。
3. 建立统一基础设施接入方式。
4. 建立高可靠与高可观测保护机制。
5. 建立明确的演进路径，支持从聚合入口平滑拆分。

#### 5.4.2 后端分层规范

后端统一采用四层职责：

1. 接口接入层：HTTP 接口、参数接收、认证入口、返回封装、请求上下文。
2. 应用服务层：用例编排、事务边界、跨模块协调。
3. 领域规则层：业务规则、状态流转、约束校验。
4. 基础设施层：数据库、缓存、对象存储、日志、任务、限流、监控接入。

#### 5.4.3 模块边界规范

核心模块至少覆盖：

1. `auth`：登录、刷新、会话、多端控制、登录日志。
2. `system`：系统配置、菜单、权限、监控、更新检查。
3. `user/org`：用户、部门、用户归属关系。
4. `iam`：角色、菜单权限、接口权限、数据范围、权限快照。
5. `dict/config`：字典、平台配置、租户配置、加密配置。
6. `file`：上传、下载、预览、元数据、存储空间、访问控制。
7. `message`：站内信、推送、归档、投递日志。
8. `plugin`：插件上传、安装、升级、回滚、运行时资源。
9. `ai`：员工、模型服务、知识库、工具治理、对话和分享。
10. `payment`：支付服务商、订单、退款、Webhook、Outbox。
11. `audit/task`：日志、审计、异步任务、内部作业。

#### 5.4.4 多租户上下文规范

1. 租户上下文是一等上下文。
2. 任何受保护请求在认证后都必须建立当前租户上下文。
3. 上下文至少包含租户 ID、用户 ID、角色集、权限快照版本和会话版本。
4. 租户边界必须同时落在数据库、缓存、文件、日志、任务和限流层。
5. 服务端必须校验用户是否真正有资格进入目标租户。

#### 5.4.5 认证与会话规范

1. 使用 `Access Token + Refresh Token + 会话状态` 的混合模式。
2. Access Token 负责接口访问。
3. Refresh Token 负责续期。
4. 会话状态负责记录会话版本、权限版本、踢下线控制和安全策略。
5. 必须预留单端登录、多端限制和高敏感账号更强会话控制能力。

#### 5.4.6 数据访问规范

1. 基础单表操作优先由 MyBatis Plus 承担。
2. 复杂查询允许手写 SQL，但必须保证可审阅、可索引、可维护。
3. 所有租户级查询必须自动带租户边界。
4. 列表查询必须分页，不允许无边界大分页。
5. 批量更新和删除必须防止误操作为全表更新。
6. 报表类重查询不得直接压主交易路径。

#### 5.4.7 缓存规范

采用两层缓存策略：

1. 本地热点缓存：少量高频只读配置和元信息。
2. Redis 分布式缓存：会话、权限快照、字典、菜单树、租户配置、任务状态、限流计数。

统一要求：

1. 缓存 key 必须显式带环境、模块、租户、用户等维度。
2. 角色变更、菜单变更、配置更新、租户切换、用户移出租户等场景必须刷新缓存或变更版本。

#### 5.4.8 限流、防刷与幂等规范

至少支持以下维度：

1. IP 维度。
2. 用户维度。
3. 租户维度。
4. 接口维度。
5. 客户端维度。
6. 全局维度。

登录、导出、状态切换、批量提交、消息发送、支付请求等高风险动作必须具备防重复提交或幂等控制。

#### 5.4.9 异步任务规范

任务中心至少覆盖：

1. 导入导出。
2. 报表生成。
3. 批量消息。
4. 文件处理。
5. Outbox 中继。
6. 定时汇总。

任务记录至少包含：

1. 任务 ID。
2. 租户 ID。
3. 用户 ID。
4. 状态。
5. 执行结果。
6. 失败原因。
7. 重试次数。
8. 执行日志。

#### 5.4.10 文件与对象存储规范

1. 文件能力必须平台化，不允许业务各自绕过文件中心。
2. 上传、下载、删除、元数据记录、访问控制必须统一收口。
3. 对象存储路径建议按环境、租户、业务域、日期分层。
4. 私有文件默认不得裸链访问，应通过受控下载或预签名策略暴露。
5. 重要文件必须落库记录元数据。

#### 5.4.11 日志、审计与异常处理规范

日志要求：

1. 应用日志至少包含 `traceId`、`requestId`、`tenantId`、`userId`、路径、耗时、结果码。
2. 不得记录密码、完整 token、完整身份证号、完整手机号等敏感信息。

审计要求：

1. 用户管理、角色授权、菜单调整、配置修改、租户切换、文件删除、插件管理、支付配置等必须进入审计日志。
2. 登录成功、登录失败、权限拒绝、异常切换尝试等安全行为必须独立记录。

异常处理要求：

1. 统一全局异常处理器负责转换标准响应。
2. 参数异常、业务异常、权限异常、租户异常、限流异常、依赖异常必须可识别。
3. 所有异常响应必须带 `requestId` 或 `traceId`。

#### 5.4.12 配置、监控与部署规范

配置至少分为：

1. 环境配置。
2. 平台配置。
3. 租户配置。

统一要求：

1. 敏感配置必须支持加密存储和审计。
2. 健康检查、版本信息、Redis 指标、服务指标必须统一暴露。
3. 主链路优先保护，外部依赖异常时应允许降级而不是拖垮主业务。
4. 所有外部访问必须设置超时。
5. 部署形态以容器化聚合后端为主，支持版本化、灰度和快速回滚。

#### 5.4.13 后端开发红线

1. 严禁控制器直接操作持久层。
2. 严禁把租户隔离长期建立在手工拼接条件上。
3. 严禁每个模块自定义一套缓存 key 规则。
4. 严禁把导入导出做成同步阻塞接口。
5. 严禁把异常堆栈原样返回前端。
6. 严禁核心写操作没有审计日志。
7. 严禁依赖调用无超时控制。
8. 严禁权限校验只做前端不做后端。

### 5.5 多租户原则

1. 共享应用、共享基础设施，优先采用逻辑隔离。
2. 默认共享数据库共享表，通过 `tenant_id` 建立租户级边界。
3. 对重点租户预留独立数据库、独立缓存前缀、独立对象存储目录和独立部署能力。
4. 租户上下文必须贯穿认证、授权、SQL、缓存、文件、日志、任务和消息链路。
5. 前端不作为租户边界的最终控制者，真实边界必须由后端保证。

## 7. 核心业务流程

### 7.1 登录与访问流程

1. 用户进入登录页。
2. 系统展示当前可用登录能力，包括账号密码、验证码、短信/邮箱验证码、微信登录、Passkey 等能力。
3. 用户完成登录校验。
4. 系统生成访问令牌、刷新令牌和会话信息。
5. 系统拉取当前用户、角色、菜单和权限快照。
6. 前端根据权限渲染可访问菜单和默认首页。
7. 用户进入工作台或对应功能页面。

### 7.2 系统管理流程

1. 管理员进入系统设置或用户中心。
2. 维护部门、用户、角色和菜单。
3. 为角色配置菜单权限、按钮权限、数据范围和默认首页。
4. 为用户分配角色和部门。
5. 权限变更后，用户重新进入系统时权限快照更新。
6. 关键写操作进入审计日志。

### 7.3 AI 使用流程

1. AI 管理员配置模型服务、AI 员工、工具策略和知识库。
2. AI 管理员上传知识库文档并触发索引或重建索引。
3. 普通用户进入 AI 助手页面，选择或使用默认 AI 员工发起对话。
4. 系统支持普通响应和流式响应，并可返回工具调用建议、工具调用结果和知识引用。
5. 用户可管理会话、导出会话或生成分享链接。
6. AI 调用、工具调用和敏感行为进入审计或治理记录。

### 7.3.1 通知与内容治理流程

1. 管理员进入通知中心，配置站内通知、邮箱通知、微信公众号通知等渠道参数。
2. 管理员可执行测试发布，验证通知链路是否可用。
3. 业务侧表单提交或导入文本内容时，系统按启用状态接入敏感词检测。
4. 如果命中敏感词规则，系统返回用户可理解的拦截提示，并记录治理事件。
5. 敏感词插件管理员可维护词条、导入词库、启停策略和检查结果。

### 7.4 文件与下载流程

1. 用户进入我的文件或全部文件中心。
2. 用户上传文件并填写分类、标签、备注、存储空间等信息。
3. 系统完成文件安全校验、元数据记录和存储。
4. 用户可按权限预览、下载、删除文件。
5. 管理员可管理存储空间并进行连通性测试。
6. 下载中心提供可公开或按权限分发的资源入口。

### 7.5 插件管理流程

1. 插件管理员上传插件包。
2. 系统解析插件定义、版本、权限、菜单和安全策略。
3. 插件管理员执行安装、升级、回滚、启用、停用或卸载。
4. 用户通过插件运行时页面访问已授权插件。
5. 系统记录插件生命周期操作和运行日志。

### 7.6 部署运维流程

1. 前端部署到 Vercel，默认通过 `/api` 和 `/ws` 转发到后端公网域名。
2. 后端通过 Docker Compose 启动 `lumira-server`、API proxy、MySQL、Redis、XXL-Job 等组件。
3. 部署脚本执行环境检测、构建、启动和健康检查。
4. 运维人员通过健康接口、日志、监控页面和可观测性看板检查系统状态。
5. 重要变更前执行备份，异常时通过恢复脚本回滚数据与文件。

## 10. 接口需求

### 10.1 接口规范

1. 内部业务接口以 `/api/v1/*` 为主，AI 当前使用 `/api/ai/*`。
2. 统一响应结构应包含业务码、消息、用户提示、数据、请求 ID、路径和时间戳。
3. 文件下载、预览和流式响应可以不使用普通 JSON 响应，但必须保留鉴权、错误处理和审计约束。
4. 认证接口必须支持登录、登出、刷新 token、当前用户和登录能力查询。
5. 管理类接口必须进行权限校验，禁止只依赖前端菜单隐藏。
6. 分页接口必须限制 `pageSize`，避免无约束大分页。
7. 写接口必须进行服务端参数校验，并返回可识别业务错误。

## 12. 非功能需求

### 12.1 安全性

1. 登录凭证不得以明文形式直接暴露在网络传输和日志中。
2. 支持验证码、二次验证、Passkey、登录保护等增强认证能力。
3. 所有管理接口必须进行后端鉴权。
4. 敏感配置字段必须加密存储或脱敏展示。
5. 插件运行时必须受安全策略限制，防止越权访问平台资源。
6. 生产环境只允许配置明确的前端来源，避免开放式 CORS。
7. 关键操作必须记录审计日志。

### 12.2 可用性

1. 系统应提供健康检查接口，支持部署脚本和外部监控探测。
2. 登录、工作台、用户权限、文件下载、AI 对话等主链路出现异常时，应给出可理解提示。
3. 部署脚本应支持查看状态、查看日志、停止、重建等常用运维动作。
4. 小型服务器上应通过限流、连接池和资源上限避免系统被流量打满。

### 12.3 可维护性

1. 前端按 `pages`、`services`、`auth`、`theme`、`plugins` 等职责组织。
2. 后端按 `services/*-service` 和 `libs/*` 组织，禁止跨模块随意穿透内部实现。
3. 新增业务能力必须明确模块 owner、表归属、API 契约和权限标识。
4. 数据库变更必须通过迁移脚本管理。
5. 文档、脚本、监控和部署说明默认以 `lumira-server` 为后端运行入口。

### 12.4 可扩展性

1. 当前采用单体微服务运行模式，但保留模块化服务边界。
2. 文件、消息、插件、本地化、支付、AI 等模块可在未来按 owner 和契约逐步拆分。
3. 插件体系支持业务能力以插件方式扩展。
4. 国际化体系支持后续多语言 UI 和业务文案发布。
5. AI 工具策略支持后续接入更多企业内部工具。

### 12.5 性能与容量

1. 分页列表必须控制默认页大小和最大页大小。
2. 登录、验证码、公开配置和 API 入口需要限流保护。
3. Redis 使用内存上限和淘汰策略，避免缓存膨胀拖垮宿主机。
4. Docker 日志需要轮转，避免日志撑满磁盘。
5. 可通过轻量压测脚本验证演示环境的并发承载能力。

### 12.6 可观测性

1. 系统应暴露健康检查和版本信息。
2. 支持服务监控、Redis 监控和 API 文档查看。
3. 支持按需启用 Prometheus 指标、Grafana 看板、Loki 日志、Tempo Trace 和 OpenTelemetry。
4. 审计日志应支持登录、操作、AI 调用、验证行为等维度查询。

### 12.7 第一阶段落地边界

第一阶段不追求铺满所有垂直业务，而是要确保平台底座形成可复用的最小闭环。当前阶段重点已经覆盖：

1. 登录体系与统一认证入口。
2. 权限模型、菜单路由与页面访问控制。
3. 用户、角色、部门、字典、配置等系统管理能力。
4. 文件、消息、审计、监控、健康检查和部署链路。
5. AI 助手、知识库、插件、本地化、支付配置等平台扩展能力。

## 15. 风险与约束

| 风险 | 影响 | 应对策略 |
| --- | --- | --- |
| 单体微服务继续膨胀 | 后续模块增多后构建和维护复杂度上升 | 保持 owner、契约和数据边界，必要时按模块拆分 |
| AI 服务依赖外部模型 | 模型不可用会影响 AI 助手体验 | 支持模型服务配置、连通性测试、错误提示和降级 |
| 插件运行时安全 | 插件可能带来越权或资源风险 | 保留插件安全策略、权限声明、资源隔离和日志审计 |
| 小服务器资源有限 | 高并发时可能出现性能瓶颈 | 使用限流、连接池、Redis 内存上限、日志轮转和轻量压测 |
| 配置密钥管理复杂 | 泄露会造成安全问题 | `.env` 不入库，敏感字段加密，展示脱敏 |
| 权限模型复杂 | 配置错误会导致用户看不到或看到不该看的功能 | 提供权限树、默认角色、审计日志和验收用例 |

## 17. 结论

Lumira 已经具备企业级 SaaS 智能应用平台的核心产品形态。它既包含传统管理后台必需的用户、角色、权限、菜单、配置、审计和监控，也加入了 AI 助手、知识库、工具调用、插件管理、国际化、文件中心、消息中心和支付配置等扩展能力。

从需求角度看，当前版本已经能够支撑“可登录、可授权、可配置、可审计、可扩展、可部署、可演示”的完整闭环。后续工作重点不应再盲目扩展大功能，而应围绕演示数据、租户运营、AI 治理、插件生态、运维交付和模块拆分路线继续打磨。

## 18. 接口级需求规格

本章节改为逐接口编写。每个接口单独说明“做什么、请求字段、返回字段、字段格式、页面呈现方式”，避免把接口和模型混在一起难以查阅。

### 18.1 统一约定

除文件下载、文件预览、SSE 流式响应、插件静态资源外，接口统一返回 `ApiResponse<T>`。

| 字段 | 类型 | 格式 | 说明 | 页面呈现 |
| --- | --- | --- | --- | --- |
| code | string | `A0000` | 业务状态码 | 一般不直接展示；异常时用于判断分支 |
| message | string | `success` | 技术描述 | 失败时作为兜底提示 |
| userMessage | string? | `验证码错误` | 用户可读提示 | Toast、表单报错、弹窗 |
| data | object/array/string/boolean | 业务数据 | 具体见每个接口 | 按页面场景渲染 |
| requestId | string? | `trace_xxx` | 链路 ID | 错误详情、审计排障 |
| timestamp | string | `2026-06-10T22:00:00` | 响应时间 | 一般不展示 |
| path | string? | `/api/v1/auth/login` | 当前路径 | 错误详情 |

分页接口统一返回 `PagedResult<T>`，其中 `records` 对应表格数据源，`total/pageNo/pageSize` 对应分页器。

### 18.10 字段呈现验收规则

1. 每个列表接口的 `records[]` 必须能直接作为表格数据源使用，`id` 或业务编码必须稳定。
2. 每个状态字段必须明确文案、颜色和筛选项，不能只返回裸值不解释。
3. 每个 URL 图片字段必须支持加载失败占位；Logo、头像、背景图都要有默认态。
4. 每个 secret 字段只能在编辑时输入，返回时只能是 `configured` 标志或脱敏值。
5. 每个时间字段必须统一格式化显示，空值显示 `-`。
6. 每个金额字段如果使用最小单位，前端必须转换后再展示。
7. 每个长文本字段必须支持摘要和全文两种呈现，不应在表格中直接撑开布局。
8. 每个上传接口都必须有进度、成功反馈和失败原因。
9. 每个高风险接口，如删除、停用、回滚、撤回、退款，必须配确认弹窗。
10. 当前第 17 章优先覆盖前端真实使用接口；`/internal/*` 等内部契约建议在后续补充单独的《内部接口设计说明》。
