## 2. 项目测试对象

### 2.1 系统形态

当前系统采用“单体微服务”运行模式，默认后端统一入口为 `services/legendary-server`，聚合以下模块：

- 认证模块：`auth-service`
- 系统模块：`system-service`
- 文件模块：`file-service`
- 消息模块：`message-service`
- 插件模块：`plugin-service`
- 国际化模块：`localization-service`
- 支付模块：`payment-service`
- 任务模块：`job-executor`

前端工程位于 `frontend/`，基于 React、TypeScript、Umi Max、Ant Design 和 ProComponents。

### 2.2 测试重点

本系统属于平台底座类产品，测试重点不是单一页面，而是以下四类能力：

1. 主业务链路是否可用
2. 权限、租户、审计等横切能力是否正确
3. 平台级稳定性、安全性、可恢复性是否达标
4. 前后端、脚本、部署、观测链路是否联动正常

## 3. 测试范围

### 3.1 纳入测试范围

- 登录认证与会话管理
- 用户、角色、菜单、部门、权限快照
- 平台配置、安全配置、个性化配置
- 字典、监控、审计、在线用户
- AI 助手、知识库、AI 员工、模型服务
- 文件上传、下载、删除、存储空间管理
- 站内消息、通知中心、WebSocket 推送
- 插件管理、插件运行时、安全词
- 国际化语言、命名空间、词条、发布
- 支付配置、支付回调、交易状态流转
- Outbox、内部任务、作业执行
- Docker 部署、健康检查、备份恢复、可观测性

### 3.2 暂不纳入首轮深测的范围

- 未落地的外部第三方真实支付联调全量场景
- 未接入生产凭证的真实短信、邮件、微信公众号全链路压测
- 未来拆分为独立微服务后的跨进程网络故障注入

这三类内容可以作为第二阶段专项测试。

## 4. 测试目标与准入准出

### 4.1 测试目标

- 核心功能链路可稳定完成
- 权限控制真实有效，前后端口径一致
- 高风险写操作具备幂等、防重复提交和审计记录
- 文件、消息、AI、支付、插件等扩展能力在异常情况下可控降级
- 部署脚本、健康检查、回滚与恢复路径可执行

### 4.2 提测准入标准

- 需求范围明确，接口与交互已冻结到当前迭代
- 自测完成，研发已通过基本构建检查
- 后端至少通过：

```bash
./mvnw -DskipTests package
```

- 前端至少通过：

```bash
corepack pnpm --dir frontend typecheck
corepack pnpm --dir frontend build
```

- 关键自动化测试至少通过：

```bash
./mvnw test
corepack pnpm --dir frontend test
```

- 测试环境可访问，数据库与 Redis 已准备

### 4.3 测试通过标准

- P0 缺陷为 0
- P1 缺陷为 0
- P2 缺陷已评估且不影响上线主链路
- 核心功能用例通过率 100%
- 非核心功能用例通过率不低于 95%
- 冒烟用例通过率 100%
- 部署校验脚本通过

## 6. 测试方法与分层

### 6.1 测试分层

建议采用以下五层测试策略：

1. 单元测试：方法级、类级规则验证
2. 集成测试：模块内接口、数据库、Redis、事件链路验证
3. 接口测试：认证、参数、权限、响应结构、错误码验证
4. UI 功能测试：页面流程、交互、表格、表单、状态切换验证
5. 端到端验收测试：前端、后端、数据库、缓存、脚本、观测联合验证

### 6.2 测试类型

- 正向功能测试
- 逆向异常测试
- 边界值测试
- 权限与安全测试
- 并发与幂等测试
- 兼容性测试
- 性能与稳定性测试
- 恢复与回滚测试

### 6.3 风险驱动原则

优先深测以下高风险区域：

- 登录、刷新 token、二次验证、Passkey
- 用户、角色、菜单、权限快照
- 高风险写接口的重复提交控制
- 文件上传与下载鉴权
- AI 工具调用授权与知识库处理
- WebSocket 消息实时推送
- 插件运行时安全
- 支付回调幂等
- Outbox 投递与任务执行

### 7.1 本地联调环境

适用场景：开发自测、问题复现、模块回归。

启动命令：

```bash
node scripts/start-platform.mjs
```

访问入口：

- 前端：`http://localhost:8000`
- 后端：`http://localhost:8080`
- 健康检查：`http://localhost:8080/actuator/health`

适用场景：提测、联调、回归、冒烟。

建议使用生产形态近似环境，基于 `deploy/docker-compose.prod.yml` 启动，且使用独立数据库、独立 Redis、独立域名和独立密钥配置。

启动命令：

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.prod.yml up -d --build
```

适用场景：发布前验证、回滚演练、观测校验。

```bash

```

## 9. 统一检查点

所有接口和页面测试都要检查以下通用项：

### 9.1 接口通用检查

- URL 是否符合 `/api/v1/*` 规范
- HTTP 方法是否正确
- 响应壳是否包含 `httpStatus`、`code`、`message`、`data`、`requestId`、`path`、`timestamp`
- 错误码是否可识别
- 参数错误是否返回 400 或明确业务码
- 未登录是否返回 401
- 无权限是否返回 403
- 重复提交是否返回明确提示
- 日志与审计是否记录

### 9.2 页面通用检查

- 首屏可加载
- 加载态、空态、异常态完整
- 表单校验位置与文案正确
- 主操作按钮状态正确
- 操作成功后页面状态同步刷新
- 错误提示不泄露后端堆栈
- 权限不足时页面跳转 403 或显示受限态
- 切换租户后菜单、权限、缓存同步刷新

## 10. 冒烟测试集

每次提测和上线前必须执行如下冒烟用例：

1. 登录页打开正常，验证码正常
2. 账号密码登录成功
3. 当前用户信息与菜单正常返回
4. 用户列表页可打开并翻页
5. 角色管理页可打开并查看权限树
6. 菜单管理页可打开并编辑一条菜单
7. 文件上传和下载正常
8. 通知中心可查看未读消息
9. AI 助手页面可打开
10. 插件管理页可打开
11. 国际化管理页可查询
12. 系统监控页可打开
13. 健康检查接口返回 UP
14. 部署检查脚本通过

### 10.1 页面级手工测试执行建议

为了避免“知道模块名，但不知道实际该点哪个页面、点到哪一步”，手工测试建议统一按页面执行，而不是只按后端模块执行。

推荐执行顺序：

1. 登录页与会话建立
2. 工作台与下载中心
3. 用户中心页面：用户、部门、在线用户、角色、个人资料、我的文件
4. 系统设置页面：菜单、字典、资料字段、个性化、安全、验证、支付、通知、AI 员工、插件、本地化、全部文件、监控、API 文档、审计
5. AI 页面：助手、知识库、分享页
6. 插件页面：敏感词插件、插件运行时
7. 异常页：403、404

## 12. 权限与安全专项测试

### 12.1 权限专项

必须覆盖以下场景：

- 无菜单权限但直接输入 URL 访问页面
- 前端隐藏按钮但通过接口直接调用写操作
- 用户切换租户后使用旧页面缓存继续提交
- 平台超管进入租户视角后的边界控制
- 只读账号尝试编辑系统配置

### 12.2 安全专项

必须覆盖以下检查：

- 登录暴力尝试限制
- 验证码绕过检查
- token 篡改与过期校验
- 文件类型伪造上传
- 大文件与恶意文件上传
- 敏感配置脱敏展示
- 错误响应不输出堆栈
- 插件安装签名校验
- WebSocket 未授权连接
- 支付回调签名伪造

## 13. 非功能测试

### 13.1 性能测试

建议至少执行以下压测：

- 登录接口：100 并发，持续 5 分钟
- 用户列表接口：200 并发，持续 10 分钟
- 文件上传接口：20 并发，按 1MB、5MB、20MB 分层测试
- AI 对话接口：20 并发，重点观察流式响应稳定性
- WebSocket 在线连接：1000 长连接模拟

- 平均响应时间
- P95、P99 响应时间
- 错误率
- CPU、内存、GC

- 平板分辨率
- 移动端窄屏关键页面

- 表格页
- 抽屉表单
- AI 助手页
- 文件中心
- 设置页

## 15. 缺陷管理规范

### 15.1 缺陷等级

- P0：系统不可用、数据错乱、严重安全问题、核心链路中断
- P1：核心功能异常、权限失效、重要接口错误、稳定性明显异常
- P2：非核心功能异常、有替代路径、体验问题但可继续测试
- P3：低风险文案、样式、提示问题

### 15.2 缺陷单最少字段

- 标题
- 所属模块
- 环境
- 前置条件
- 复现步骤
- 实际结果
- 预期结果
- 严重级别
- 截图或日志
- 是否稳定复现

### 15.3 缺陷关闭标准

- 研发修复完成
- 测试复验通过
- 关联回归用例通过
- 无新增同类回归问题

## 20. 结论

本项目测试不能只做页面点点点，也不能只看接口成功返回。必须把认证、权限、租户、审计、文件、AI、插件、支付、消息、任务、部署、恢复和观测作为一个完整平台来验证。

执行层面建议坚持三条原则：

1. 先跑主链路，再扫边界和异常
2. 先守住权限与数据安全，再追求功能完整
3. 每修一个高风险缺陷，都要补一条自动化测试
