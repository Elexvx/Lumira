# Ant Design Pro 大型 SaaS 系统接口规范与统一响应标准

## 1. 文档定位

本规范用于统一接口风格、请求与响应格式、分页标准、鉴权规则、租户透传、错误码体系、幂等要求、导入导出、文件上传、开放接口和审计约束。

## 2. 总体原则

- 语义优先。
- 统一响应。
- 租户上下文一致。
- 权限真实校验。
- 错误可识别。
- 幂等和审计前置。
- 为开放能力预留空间。

## 3. API 路径规范

- 内部接口统一以 `/api/v1/*` 为前缀。
- 路径优先表达资源，不优先表达动作。
- 路径使用小写资源风格，不使用驼峰。
- 推荐示例：
  - `/api/v1/auth/login`
  - `/api/v1/tenant/current`
  - `/api/v1/tenant/switch`
  - `/api/v1/system/users`
  - `/api/v1/iam/roles`
  - `/api/v1/files/upload`
  - `/api/v1/audit/operate-logs`

## 4. HTTP 方法规范

- `GET` 用于读取。
- `POST` 用于创建、复杂查询、提交任务。
- `PUT` 用于整体更新。
- `PATCH` 用于局部更新。
- `DELETE` 用于删除。

复杂查询可允许 `POST /search` 风格，但必须语义清晰。

## 5. 统一响应结构

推荐统一返回：

```json
{
  "httpStatus": 200,
  "code": "A0000",
  "message": "success",
  "userMessage": null,
  "data": {},
  "requestId": "trace_xxx",
  "path": "/api/example",
  "timestamp": "2026-03-25 10:00:00"
}
```

- `httpStatus` 表示 HTTP 状态码镜像，便于前端统一处理。
- `code` 表示业务响应码。
- `message` 表示面向排障与日志的详细描述。
- `userMessage` 表示面向用户展示的提示文案；如为空，前端可回退展示 `message`。
- `data` 表示业务载荷。
- `requestId` 用于链路追踪。
- `path` 表示当前请求路径。
- `timestamp` 用于时间标识。

文件下载和流式响应可例外，但必须保留鉴权和审计约束。

## 6. HTTP 状态码与业务码

- `200`：请求被正常处理。
- `400`：参数错误。
- `401`：未认证。
- `403`：无权限。
- `404`：资源不存在。
- `409`：资源冲突。
- `429`：限流。
- `500`：系统异常。
- `503`：服务不可用或降级。

业务码建议分层：

- `A0000`：成功。
- `B1xxx`：认证与权限。
- `B2xxx`：租户与配额。
- `B3xxx`：参数与校验。
- `B4xxx`：资源状态与冲突。
- `B5xxx`：文件与导入导出。
- `B6xxx`：限流、风控、幂等。
- `Cxxxx`：系统和依赖异常。

## 7. 请求头规范

建议统一支持：

- `Authorization`
- `X-Request-Id`
- `X-Tenant-Id`
- `X-Client-Type`
- `X-App-Version`
- `Accept-Language`

其中 `X-Tenant-Id` 可以透传，但不能作为唯一可信来源，服务端必须校验用户租户归属。

## 8. 租户透传与切换

- 租户是一级上下文。
- 租户切换建议使用专门接口。
- 所有租户级接口必须由服务端自动附加租户约束。
- 不能让前端决定数据边界。

## 9. 分页规范

请求建议统一为：

```json
{
  "current": 1,
  "pageSize": 20,
  "sorter": {
    "createdAt": "descend"
  },
  "filters": {
    "status": [1],
    "keyword": "admin"
  }
}
```

响应建议统一为：

```json
{
  "code": "A0000",
  "message": "success",
  "data": {
    "list": [],
    "total": 0,
    "current": 1,
    "pageSize": 20
  }
}
```

分页大小必须限制，禁止超大分页直接扫表。

## 10. 写接口规范

- 创建用 `POST`
- 整体更新用 `PUT`
- 局部状态更新用 `PATCH`
- 删除用 `DELETE`

状态更新、批量操作、导入导出都应具备清晰的路径语义。

## 11. 参数校验规范

- 所有写接口必须做服务端校验。
- 失败时返回统一业务码和可定位的字段错误。
- 不能依赖前端校验作为安全边界。

## 12. 幂等与防重复提交

- 高风险动作要考虑幂等键。
- 创建、审批、导入、导出、发送、状态切换要重点保护。
- 重复提交时返回统一业务码，不要抛通用异常。

## 13. 权限与数据范围

- 接口入口做功能权限校验。
- 资源加载后做租户归属校验。
- 数据访问层做数据范围过滤。
- 高风险操作写审计日志。

## 14. 文件与流式接口

- 上传统一 `POST /api/v1/files/upload`
- 下载必须先鉴权、再审计、再输出流
- 私有文件建议使用签名或代理下载

## 15. 导入导出与任务接口

- 导入导出尽量任务化。
- 建议有任务创建、任务查询、任务结果查询三类接口。
- 大文件和复杂报表不要同步阻塞请求线程。

## 16. 开放接口预留

- 建议使用 `/openapi/v1/*`
- 独立签名、时间戳、重放保护、限流和调用日志
- 内部接口和开放接口必须边界清晰

## 17. 日志与异常

- 所有敏感接口应具备审计日志。
- 统一全局异常处理，输出标准响应壳。
- 禁止把默认堆栈直接暴露给前端。

## 18. 第一阶段最小接口清单

- 认证：登录、登出、刷新 token、当前用户、权限快照
- 租户：当前租户、租户列表、切换租户
- 用户：列表、详情、新增、编辑、状态变更、角色分配
- 角色：列表、详情、新增、编辑、授权
- 菜单：树查询、排序、状态变更
- 字典：类型、字典项、缓存刷新
- 配置：查询、修改
- 文件：上传、下载、删除
- 审计：登录日志、操作日志
- 任务：任务查询、导入导出任务状态
