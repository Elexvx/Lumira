# 赛事功能重叠审计（2026-08-13）

## 审计范围

- 本地预览：`http://127.0.0.1:8899`
- 赛事：`9af5fde3-1078-4509-91b8-11a77ed4756f`
- 覆盖入口：赛事工作空间、数据管理、专家与评审、支付、证书、审计
- 方法：当前浏览器点击截图 + 前端路由/组件 + API 分支 + 后端工作空间能力映射对账
- 本次只做审计，没有修改菜单、路由或业务代码。

## 用户目标

以“选定赛事后的工作空间”为赛事运营主入口，减少同一任务在全局菜单和工作空间中的重复入口，同时保留确有必要的跨赛事运营能力。

## 总体结论

当前存在两种不同性质的重叠：

1. **真实重复，需要合并**：工作空间“报名数据”与“材料”是两个路由、两个页签，但加载同一个组件，内容和操作完全相同。
2. **范围复用，需要重新命名或收口入口**：全局报名、评审、支付、证书与工作空间复用同一页面组件，差异只是“先选赛事”与“已绑定当前赛事”。其中全局报名页没有形成跨赛事总览，重复最明显；支付、评审、证书仍有跨赛事运营价值。

## 优点

- 工作空间已由后端 `allowedModules` 和 `capabilities` 控制可见模块，数据请求也有赛事 UUID 作用域，不是单纯前端过滤。
- 报名、评审、支付、证书通过共享组件实现全局/赛事两种作用域，代码复用本身是合理的。
- 浏览器结构中菜单、页签、表单标签和表格语义均可识别；当前主要问题是信息架构和范围命名，而不是基础控件缺失。

## 主要发现

### [P1] 工作空间“报名数据”和“材料”完全重复

- 证据：
  - `/competitions/:competitionUuid/registrations` 与 `/competitions/:competitionUuid/materials` 都挂载 `CompetitionRegistrationDataPage`。
  - 页面组件没有根据 `pathname` 或模块键切换视图。
  - 后端只要具备报名读取能力，就同时返回 `registrations` 和 `materials` 两个模块。
  - 截图 `02-workspace-registration-data.jpg` 与 `03-workspace-materials.jpg` 的筛选项、表头、导出操作和空状态相同，只有选中页签不同。
- 影响：用户点击“材料”会认为进入了材料任务，却仍看到报名团队表；页签切换没有带来新的工作内容。
- 建议：合并为一个“报名与材料”页签；将 `/materials` 保留为兼容重定向到 `/registrations`。如果未来确实需要独立材料页，则必须提供材料中心视图，例如阶段、提交次数、最新提交时间、完整度、缺失项和文件数。

### [P1] 全局“报名团队资料”与工作空间报名页高度重复

- 证据：全局 `/competitions/registrations` 与工作空间报名/材料路由使用同一个组件。
- 全局页只有多一个赛事选择；未选择赛事时直接返回空数据，并不是跨赛事聚合列表。
- 截图 `04-global-registration-dossier.jpg` 与工作空间报名页的表头、导出动作和资料抽屉入口一致。
- 影响：用户无法理解为什么已经进入某赛事后，还需要回到“数据管理 > 报名团队资料”做同一件事。
- 建议：默认侧栏移除“报名团队资料”，从“赛事管理”进入工作空间；保留旧路由做兼容。如果确有中央运营需求，应把全局页升级并重命名为“跨赛事报名查询”，支持真正的多赛事聚合、批量筛选和跳转赛事工作空间。

### [P2] 工作空间内仍显示赛事选择条件

- 证据：`02`、`03` 两张截图中，工作空间顶部已固定赛事，但查询区仍出现“赛事 / 请选择要查看的数据表”。
- 影响：形成双重赛事上下文，用户会怀疑查询范围是否真的绑定当前赛事。
- 建议：工作空间模式完全隐藏赛事筛选，只显示当前赛事标题和不可变作用域说明。

### [P2] 评审复用合理，但全局与单赛事入口没有范围说明

- 全局 `/expert-review/reviews` 与工作空间 `/reviews` 使用同一个 `CompetitionReviewPage`；工作空间调用 UUID 作用域 API，全局版本显示赛事选择。
- 截图 `01-workspace-reviews.jpg` 表明工作空间版已经适合作为单赛事执行入口。
- 建议：工作空间继续使用“评审”；全局入口改为“跨赛事评审工作台”或“评审运营中心”，只面向需要跨赛事调度的角色。

### [P2] 支付复用具有业务价值，但命名容易被理解为重复

- 全局 `/payments/management` 与工作空间 `/payments` 使用同一个 `PaymentPage`；全局调用全部报名支付列表，工作空间调用赛事 UUID 支付列表。
- 截图 `05-global-payment-management.jpg` 体现全局账务视角，包含赛事、团队、项目等列。
- 建议：全局改名为“全局支付流水”或“支付对账”；工作空间保留“支付”。二者应在页面说明中明确“全部赛事”与“当前赛事”。

### [P2] 证书生成/记录是同组件双作用域，证书模板则是全局独有能力

- 全局 `/certificates/generate`、`/certificates/records` 与工作空间证书生成/记录复用同一页面和不同作用域 API。
- 全局“证书模板”“我的证书”并未被工作空间替代，应继续保留。
- 建议：全局根入口命名为“证书中心”，保留模板、跨赛事生成和全局记录；工作空间“证书”只承担当前赛事授奖、制证和记录。

## 不属于重复的入口

- “赛事管理”：赛事列表、新建和进入工作空间，属于上层入口，应保留。
- 顶层“报名”：面向参赛者的报名流程，不是管理员查看报名团队资料。
- “下载中心”：承接导出和材料打包的异步任务，不等同于报名/材料页面。
- “活动管理”：与赛事工作空间是不同业务对象。
- “赛事审计”与系统“审计中心”：前者只记录当前赛事配置变更，后者是平台登录/操作审计。

## 推荐实施顺序

1. 合并工作空间“报名数据/材料”，并为旧 `/materials` 路由保留兼容重定向。
2. 从默认数据管理侧栏移除“报名团队资料”；若保留，则升级为真正的“跨赛事报名查询”。
3. 为全局评审、支付、证书入口补充“跨赛事/全局”命名，工作空间继续使用短名称。
4. 增加导航契约测试：两个一级可见入口若挂载同一组件，必须声明不同的作用域目的；每个工作空间模块必须产生不同的主要任务视图。

## 审计步骤与健康状态

1. **赛事工作空间评审** — 健康：功能边界成立，但与全局评审名称需区分。证据：`01-workspace-reviews.jpg`。
2. **赛事工作空间报名数据** — 有风险：与材料页完全重复，并出现多余赛事筛选。证据：`02-workspace-registration-data.jpg`。
3. **赛事工作空间材料** — 不健康：没有独立材料任务视图。证据：`03-workspace-materials.jpg`。
4. **全局报名团队资料** — 有风险：只是同一页面增加赛事选择，未形成跨赛事总览。证据：`04-global-registration-dossier.jpg`。
5. **全局支付管理** — 基本健康：全局运营价值存在，但需要范围命名。证据：`05-global-payment-management.jpg`。
6. **后续工作空间支付/证书浏览** — 阻断：审计过程中登录会话到期并跳转登录页。代码/API 对账已完成，但没有继续声明浏览器视觉验收。证据：`06-authentication-blocker.jpg`。

## 可访问性风险与证据限制

- 两个名称不同但内容相同的页签会让键盘和读屏用户误以为上下文已切换，属于状态沟通问题。
- 当前截图只能确认可见结构和语义角色，不能证明完整键盘顺序、焦点管理或读屏播报符合 WCAG。
- 登录会话在打开工作空间支付时到期，因此支付和证书的“同组件双作用域”结论来自当前代码/API 对账，不作为本轮完整浏览器视觉验收结论。
