# Lumira 项目前端开发规范

## 1. 文档定位

本文档是 Lumira 项目的前端开发规范，面向当前仓库中的 `lumira-ui/` 工程。

它不是通用前端最佳实践集合，而是结合本项目当前技术栈、目录结构、管理后台形态、权限模型、租户模型、接口风格和测试方式整理出的项目级约束。

目标是让新增页面、组件、状态、接口调用和交互行为都保持同一套工程语言，避免“功能能跑，但越来越难维护”的情况。

## 2. 适用范围

- 适用于 `lumira-ui/src/` 下所有业务页面、布局、组件、hooks、服务层和工具层代码。
- 适用于登录页、管理后台、AI 页面、系统设置、文件中心、消息中心等全部前端功能。
- 适用于新增页面开发、老页面重构、样式治理、请求封装、权限接入和测试补充。

## 3. 当前项目基线

### 3.1 当前技术栈

根据 `lumira-ui/package.json`，当前前端工程基线如下：

- `React 19.2.6`
- `TypeScript 6.0.3`
- `@umijs/max 4.6.51`
- `antd 6.3.7`
- `@ant-design/pro-components 3.1.12-0`
- `@tanstack/react-query 5.100.9`
- `vitest 4.1.6`
- 包管理器：`pnpm 10.33.0`

### 3.2 当前项目定位

当前前端不是营销官网，也不是纯展示站，而是以中后台管理端为主的企业级 SaaS 平台界面，核心特点如下：

- 以桌面端管理操作为主。
- 兼顾平板端和移动端关键路径。
- 强依赖菜单、权限、租户、登录态和统一请求层。
- 页面以列表、表单、详情、配置、消息、会话类工作台为主。

### 3.3 当前工程核心目录

| 目录 | 说明 |
| --- | --- |
| `lumira-ui/src/layouts/` | 全局壳层、AI 布局、设置页布局、顶部动作区 |
| `lumira-ui/src/pages/` | 路由页面 |
| `lumira-ui/src/services/` | 按业务域拆分的接口封装 |
| `lumira-ui/src/hooks/` | 复用逻辑 |
| `lumira-ui/src/plugins/` | 插件运行时、注册与装载 |
| `lumira-ui/src/theme/` | 主题与反馈桥接 |
| `lumira-ui/src/query/` | React Query 基础封装 |
| `lumira-ui/src/utils/` | 工具函数 |
| `lumira-ui/src/types/` | 公共类型 |
| `lumira-ui/src/i18n/` | 国际化运行时能力 |
| `lumira-ui/src/routes/` | 路由元信息 |

### 3.4 首轮工程底座约束来源

当前前端规范并不是从零抽象出来的，而是基于项目第一轮工程底座初始化阶段沉淀出来的。该阶段的核心目标不是快速堆页面，而是先把工程骨架搭稳，具体包括：

1. 建立可长期扩展的前端标准工程骨架。
2. 建立统一目录结构与分层边界。
3. 建立统一请求封装、统一运行时配置入口和统一错误反馈机制。
4. 建立认证、租户、响应式、缓存、权限表达等基础能力的标准接入位置。
5. 保证项目具备本地启动、联调和后续迭代能力。

这意味着本项目的前端规范首先服务于“壳层稳定、结构稳定、入口稳定”，而不是短期演示页面数量。

### 3.5 基础骨架最小落地要求

前端新增能力或重构时，应默认满足以下骨架要求：

1. 使用统一请求层，而不是在页面中直接散写原始请求调用。
2. 接入统一布局体系，而不是单页自建壳层。
3. 接入统一登录态、租户上下文和权限表达能力。
4. 页面最少要能处理加载态、空态、错误态和权限态。
5. 页面目录、服务目录、hook 目录和类型目录职责要清晰。

### 3.6 布局骨架基线

项目最初即要求至少具备三类基础布局，后续新增页面仍应遵守：

1. 主业务布局：登录后的管理端主壳层。
2. 用户布局：登录、找回密码、认证等入口页。
3. 空白布局：全屏页、特殊流程页、嵌入页。

其中主业务布局至少应长期稳定提供：

- 左侧导航区域
- 顶部工具区
- 页面内容容器
- 用户菜单入口
- 租户切换入口
- 通知入口
- 响应式折叠能力

### 3.7 基础验证页面要求

即使在底座阶段，前端也应保留一组最小验证页面，用于持续验证路由、布局、权限和请求层没有被破坏。建议至少包括：

1. 登录页
2. 首页或工作台占位页
3. 403 无权限页
4. 404 页面
5. 一个标准的系统管理占位页或真实管理页

### 3.8 前端本地运行基线

前端本地运行统一以 `lumira-ui/` 工程为主：

```bash
cd lumira-ui
pnpm install
pnpm dev
```

默认开发访问地址为 `http://localhost:8000`。
前端环境变量以 `lumira-ui/.env.example` 为基线，新增环境变量时必须补齐样例说明。

## 4. 前端总体原则

1. 以统一壳层为先，禁止页面各自发明布局体系。
2. 以服务层为接口唯一入口，禁止在页面中散写原始请求。
3. 以权限快照和菜单树驱动访问控制，禁止把权限字符串散落到任意组件里。
4. 以租户上下文作为一级上下文，所有缓存、请求和页面状态都要考虑租户切换。
5. 以管理端高频操作效率为目标，优先保证可扫描、可筛选、可批量处理、可回溯。
6. 以渐进复用为目标，重复两次以上的页面模式必须考虑沉淀组件。

## 5. 目录与分层规范

## 5.1 分层模型

前端代码统一分为四层：

1. 壳层：布局、导航、顶部工具区、全局容器、异常页。
2. 页面层：路由页面、页面级编排、页面状态。
3. 领域组件层：表格区、表单区、详情区、业务组件、复合交互组件。
4. 基础能力层：请求、缓存、权限、租户、主题、国际化、工具函数、类型定义。

## 5.2 页面目录规范

`pages/` 下按业务域拆分，不按技术类型拆分。

正确方向：

- `pages/system/...`
- `pages/file/...`
- `pages/message/...`
- `pages/user/...`

不建议方向：

- `pages/table/...`
- `pages/form/...`
- `pages/list/...`

## 5.3 服务目录规范

`services/` 按领域拆分，一个领域一个目录，目录内至少包含：

- 接口方法
- 类型定义
- 必要的请求数据转换

页面禁止直接拼接接口路径，必须通过 `services/*` 调用。

## 5.4 工具与业务边界

- `utils/` 只放通用工具，不放带业务语义的流程代码。
- `hooks/` 放可复用行为，不放整页业务编排。
- `components/` 放可复用组件，不放仅某一页可用的大块私有逻辑。
- 某页面私有组件优先放在页面目录内部，避免“伪公共组件”。

## 6. 命名规范

### 6.1 文件命名

- React 组件文件使用 `PascalCase.tsx`
- hook 文件使用 `camelCase.ts` 或 `useXxx.ts`
- 工具文件使用 `camelCase.ts`
- 类型文件优先使用 `types.ts`

### 6.2 组件命名

- 页面组件、布局组件、抽屉组件、弹窗组件统一使用 `PascalCase`
- 组件名要体现业务语义，例如 `MessageCenterDrawer`、`SettingsLayout`、`LoginFormFields`

### 6.3 Hook 命名

- 必须使用 `use` 前缀
- 名称表达行为，而不是实现细节，例如 `useLoginFlow`、`usePermissionSnapshot`

### 6.4 样式与 Token 命名

- 主题相关命名围绕 token、spacing、theme、runtime 展开
- 禁止在页面中堆砌魔法数字，公共间距与尺寸应优先沉淀到 `theme/`

## 7. 布局与页面骨架规范

## 7.1 布局类型

当前项目统一支持以下布局：

- 主布局：后台管理主壳层
- 用户布局：登录、找回密码、认证流程
- 设置布局：系统设置、品牌配置、偏好配置等分类场景
- AI 布局：会话、消息流、输入区、侧边信息区
- 空白布局：全屏页、嵌入页、特殊流程页

新增页面必须先判断属于哪类布局，禁止在页面内部重新搭建完整导航与顶栏。

## 7.2 页面骨架

列表页统一包含：

1. 页面标题区
2. 查询区
3. 操作区
4. 表格区或卡片区
5. 详情抽屉或跳转入口

表单页统一包含：

1. 页面标题区
2. 表单主体区
3. 提交与返回操作区
4. 保存中、校验失败、成功反馈机制

详情页统一包含：

1. 基础信息区
2. 状态信息区
3. 关联信息区
4. 审计或时间线信息区

## 7.3 查询区规范

- 查询区只负责筛选，不承载主业务说明文案。
- 常用条件前置，低频条件折叠。
- 输入框、选择器、日期范围应统一对齐。
- 不默认做“边输入边请求”，除非是专门的联想搜索场景。
- 重置按钮必须恢复到明确的默认状态。

## 7.4 表格区规范

- 列顺序优先为主信息、状态、补充信息、时间、操作。
- 操作列固定在右侧。
- 长文本必须省略并提供展开或悬浮查看。
- 状态值必须通过标签、颜色、图标等方式增强辨识度。
- 表格必须处理加载态、空态、错误态、分页态。

## 7.5 抽屉与弹窗规范

- 列表轻详情、轻编辑优先使用抽屉。
- 风险确认、轻量操作优先使用 Modal。
- 长表单、复杂向导、分步流程优先使用独立页面。
- 移动端抽屉和弹窗统一退化为全屏层。

## 8. 响应式规范

## 8.1 终端策略

- 桌面端：完整信息密度和批量操作能力。
- 平板端：保留核心操作，降低列数和信息密度。
- 移动端：保留关键高频动作，避免照搬宽表格。

## 8.2 具体要求

- 移动端列表优先退化为卡片流。
- 查询区在移动端默认折叠。
- 大量表格列不能简单依赖横向滚动兜底。
- 多按钮操作在小屏幕下应收纳为下拉菜单或更多操作。
- 标题、标签、按钮文案必须考虑窄屏换行或省略策略。

## 9. 组件复用规范

## 9.1 优先沉淀的通用组件

项目内应持续沉淀以下组件能力：

- 页面容器
- 查询条件区
- 表格外壳
- 行操作工具条
- 详情抽屉
- 状态标签
- 权限按钮
- 文件上传与图片上传
- 空态、异常态、加载态

## 9.2 复用判断标准

满足以下任一条件应考虑抽为公共组件：

1. 两个及以上页面重复使用。
2. 交互复杂，且容易出一致性问题。
3. 涉及权限、状态色、文件、租户等项目级规则。

## 9.3 组件边界要求

- 公共组件不直接依赖某个具体页面状态。
- 公共组件通过 props 或 hook 注入行为。
- 公共组件不直接耦合某个接口路径。

## 10. 路由、菜单与权限规范

## 10.1 路由原则

- 路由按业务域维护。
- 路由元信息与菜单元信息保持一致。
- 无权限页面统一进入 403。
- 无匹配路径统一进入 404。

## 10.2 菜单原则

- 菜单以服务端菜单树和权限快照为准。
- 插件菜单和内建菜单走统一装配流程。
- 菜单隐藏不等于无权限，后端仍必须做鉴权。

## 10.3 按钮权限原则

- 按钮显隐必须走统一权限判断能力。
- 页面中禁止散落硬编码权限字符串进行多处判断。
- 对高风险动作，前端禁用态与后端拒绝态都要具备。

## 11. 请求与服务层规范

## 11.1 请求入口

统一通过 `lumira-ui/src/services/common/request.ts` 及其内部能力发起请求。

页面层、组件层禁止绕过统一请求层直接构造 fetch 或第三方请求调用。

## 11.2 请求层统一职责

请求层至少统一处理：

- Token 注入
- 请求头透传
- 租户上下文透传
- 超时控制
- API 错误结构解析
- 登录失效处理
- 无权限处理
- 文件流处理
- SSE 流式响应处理
- 分页参数与响应转换

## 11.3 服务层写法要求

- 服务方法名使用明确业务语义，例如 `queryUsers`、`updateSecuritySettings`
- 不使用 `getData1`、`submitInfo` 这类弱语义命名
- 类型定义与方法定义尽量放在同域目录下
- 服务层负责做轻量数据清洗，不把后端脏格式直接扩散到页面层

## 11.4 错误反馈规范

- 面向用户的错误提示必须可理解。
- 技术错误信息可记录日志，但不直接原样展示给用户。
- 相同错误提示要通过统一反馈桥接处理，避免一页 message、一页 modal、一页静默失败。

## 12. 状态管理与缓存规范

## 12.1 全局状态边界

全局状态仅保留以下公共信息：

- 当前用户
- 当前租户
- 权限快照
- 主题偏好
- 通知数量
- 标签页状态

不应将页面筛选条件、弹窗开关、表单输入过程提升为全局状态。

## 12.2 页面状态

页面自己的筛选项、分页信息、展开项、临时选中项，应由页面或页面专属 hook 管理。

## 12.3 缓存规范

- 缓存 key 必须考虑租户维度。
- 列表缓存必须考虑筛选条件维度。
- 高敏感页面不默认保活。
- 租户切换后，旧租户缓存必须按规则清理。

## 12.4 React Query 使用规范

- 读接口优先使用 Query 管理缓存与重取。
- 写接口成功后必须明确刷新、失效或局部更新的对象。
- Query Key 必须稳定、结构化、可读。

## 13. 表单规范

## 13.1 表单字段组织

- 按业务分组组织字段，不做纯技术顺序堆叠。
- 必填项、风险项、系统项应有明显区分。
- 敏感配置字段要区分“已配置”与“真实明文值”。

## 13.2 校验规范

- 前端做基础格式校验。
- 后端做最终业务校验。
- 前端不能假设本地校验通过就一定可提交成功。

## 13.3 保存规范

- 保存前应防重复提交。
- 保存成功后要有明确反馈。
- 保存失败时应尽量保留用户已输入内容。

## 14. 文件、图片与富媒体规范

- 上传能力统一通过项目文件服务封装。
- 图片字段必须有加载失败占位态。
- 大文件、异步导入导出优先走任务机制，不在前端假设同步完成。
- 文件预览、下载、删除要明确权限和状态反馈。

## 15. 国际化与主题规范

## 15.1 国际化

- 用户可见文案优先走国际化体系。
- 不允许同一概念在不同页面出现不同文案口径。
- 错误码映射文案、状态文案、按钮文案要统一维护。

## 15.2 主题

- 颜色、间距、圆角、字号优先复用主题与 token。
- 页面中禁止大量内联样式覆盖系统主题。
- 新增主题相关能力优先落入 `theme/`，而不是散写到各页面。

## 16. 测试与质量门槛

## 16.1 基本命令

前端工程统一使用以下质量命令：

- `pnpm lint`
- `pnpm typecheck`
- `pnpm test`

按需可补充：

- `pnpm test:coverage`
- `pnpm test:smoke`

## 16.2 测试范围

以下变更应优先补测试：

- 登录流与认证流
- 请求层逻辑
- 权限裁剪逻辑
- 主题与运行时桥接
- 核心表单校验
- 复杂 hook

## 16.3 提交前检查

新增页面或重构页面至少自查：

1. 是否接入统一布局
2. 是否接入统一请求层
3. 是否处理加载、空态、异常态
4. 是否考虑权限与租户切换
5. 是否通过类型检查

## 17. 前端开发红线

1. 禁止在页面中直接散写接口路径和原始请求逻辑。
2. 禁止每个页面各自实现一套列表、抽屉、表单交互规则。
3. 禁止把权限判断完全下沉为纯前端控制。
4. 禁止缓存 key 不带租户维度。
5. 禁止在小屏设备直接照搬桌面端超宽表格。
6. 禁止把复杂业务状态塞进全局状态造成污染。
7. 禁止将后端返回的敏感字段明文长期保存在浏览器缓存。
8. 禁止把公共组件做成依赖具体页面私有逻辑的“伪公共组件”。

## 18. 推荐落地顺序

新功能开发时建议按以下顺序执行：

1. 确认页面所属业务域与布局类型
2. 先定义服务层方法和类型
3. 再搭建页面骨架与组件结构
4. 最后补权限、缓存、错误处理、测试

这样可以保证新增能力从第一天起就长在项目既有体系里，而不是后期再返工治理。
