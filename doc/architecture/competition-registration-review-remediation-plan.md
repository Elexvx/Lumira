# Lumira 赛事报名、材料与评审体系完整整改方案

**文档状态：** 研发评审稿
**版本：** V1.0
**日期：** 2026-07-29
**适用范围：** 赛事配置、学生报名、团队与项目资料、阶段材料、支付、专家评审、晋级、结果发布、证书、导出与审计
**目标读者：** 产品、研发、测试、运维、安全、赛事运营负责人

> 本方案以当前 Lumira 单体模块为实施起点，以“模块边界清晰、数据归属唯一、流程可追溯”为近期目标，以可平滑拆分为微服务为长期目标。核心结论是：每场比赛建立独立的**逻辑报名数据集**，评审独立建模，关键业务使用本地事务加 Outbox 事件协作；不采用每场比赛动态创建物理业务表，也不建立跨服务数据库联表。

## 1. 执行摘要

当前系统已经具备赛事配置、报名、团队/项目快照、阶段材料、支付联动、单分数评审、晋级规则和证书等基础能力，但报名资料查看、批量导出和完整评审闭环仍然不足。现有评审由管理员直接录入一个总分和结论，无法支撑多专家独立评审、盲审、回避、评分项版本、异常仲裁、冻结与发布审计。

本次整改分为四个层次：

1. **运营可用性整改。** 完成“报名团队资料”统一页面，按赛事查询团队、学生、项目、材料和支付状态，支持整队与整场导出、批量材料包任务。
2. **数据隔离整改。** 每场比赛建立一个逻辑报名数据集，所有报名行必须绑定数据集；普通用户只能访问本人/本团队，赛事管理员按授权赛事访问，平台管理员可以跨赛事访问。
3. **评审闭环整改。** 增加评审方案、评分表版本、评审批次、候选快照、专家分配、评分单、汇总、仲裁、定稿、发布和申诉审计。
4. **架构演进整改。** 先在 `lumira-system` 内按领域模块重构，通过 Repository、Internal API 和领域事件建立边界；达到拆分门槛后再依次拆出报名服务和评审服务。

最终业务闭环为：

**赛事发布 → 学生组队与报名 → 支付/确认 → 报名截止冻结 → 评审批次 → 专家分配 → 独立评分 → 汇总与仲裁 → 定稿 → 晋级/淘汰发布 → 下一阶段材料 → 复评/决赛 → 获奖 → 证书与归档。**

## 2. 整改目标与非目标

### 2.1 目标

- 每场比赛的数据在查询、授权、导出、归档和评审中都具有明确的数据集边界。
- 管理员可以在一个页面查看该赛事全部报名团队、学生、项目、材料和状态。
- 普通用户只能访问自己的报名数据，不能通过 ID 枚举、导出接口或文件地址读取他人数据。
- 评审支持多轮、多专家、多评分项、盲审、回避、超时改派、聚合、仲裁、定稿和发布。
- 报名关闭后，评审读取冻结快照，不受团队资料后续变化影响。
- 评审定稿后不可直接覆盖历史，只能通过有审计记录的撤回、重开或更正流程处理。
- 服务故障时不形成长同步调用链，关键业务可重试、可补偿、可追踪。
- 当前单体可以渐进整改，未来拆分微服务时不重做核心模型。

### 2.2 非目标

- 本阶段不要求立即把所有模块拆成独立部署的微服务。
- 不采用“每场比赛创建一张新的物理 MySQL 表”的方式。
- 不允许评审服务直接查询报名、团队、文件、支付服务的业务表。
- 不在一次发布中同时改造所有历史直接 SQL 债务；优先治理本方案涉及的新写入路径。

## 3. 当前能力与主要差距

### 3.1 已有能力

| 领域 | 当前能力 | 可复用资产 |
|---|---|---|
| 赛事 | 创建/草稿、赛事设置、发布、初赛/决赛阶段 | `CompetitionManagementAppService`、赛事配置与阶段表 |
| 报名 | 草稿、确认、支付联动、团队与项目信息 | `CompetitionRegistrationAppService`、Team Internal API、Payment Internal API |
| 数据集 | 新赛事自动创建逻辑数据集，报名行绑定数据集 | `competition_registration_dataset`、`competition_registration_dataset_row` |
| 材料 | 阶段表单、阶段材料提交、文件引用 | `competition_stage_form`、材料提交和值表、文件服务 |
| 运营查看 | 统一查看报名团队资料、学生、项目与材料，服务端异步 XLSX 与材料 ZIP | `/competitions/registrations` 页面、导出任务与下载中心 |
| 评审 | 阶段候选列表、单总分、晋级/淘汰结论、晋级规则 | `CompetitionReviewPage`、`competition_stage_review_result` |
| 证书 | 模板、版本、批次、记录、验真 | 证书应用服务与证书表组 |

### 3.2 核心差距

| 优先级 | 差距 | 业务风险 |
|---|---|---|
| P0 | 评审只有管理员单次总分，无专家任务和评分单 | 无法证明公平性与独立性，误操作可直接影响晋级 |
| P0 | 报名截止后未形成统一、不可变的评审候选快照 | 后续资料变更可能改变已评审依据 |
| P0 | 定稿与发布未严格分离 | 结果可能在未复核前对学生生效 |
| P0 | 文件下载授权需要与报名数据权限强绑定 | 可能通过文件 ID 绕过业务隔离 |
| P1 | 无盲审、利益冲突回避、超时改派 | 专家评审合规性和稳定性不足 |
| P1 | 无评分项/评分表版本 | 不同批次评分口径可能不一致 |
| P1 | 无离散度、异常分、缺评检测和仲裁 | 汇总结果不可控，难处理边界同分 |
| P2 | 超大材料包当前仍受单任务 512 MB 保护限制 | 后续独立 Export 服务应改为流式对象存储 multipart 写入，避免单节点内存峰值 |
| P2 | 现有报名编排仍包含较多直接 SQL | 模块边界弱，未来拆分成本高 |
| P2 | 服务间事件契约和 Outbox 未统一 | 微服务拆分后容易出现数据不一致 |

## 4. 总体架构原则

### 4.1 领域所有权唯一

每类事实只允许一个拥有方：

- 赛事服务拥有赛事、阶段、规则和时间窗口。
- 报名服务拥有报名状态、报名快照、逻辑数据集和阶段资格。
- 团队/项目服务拥有可编辑的团队与项目主数据。
- 文件服务拥有文件对象、扫描状态和下载凭证。
- 支付服务拥有订单、支付与退款事实。
- 评审服务拥有评审方案、任务、评分单、汇总和定稿。
- 消息服务拥有通知投递。
- 证书服务拥有证书模板、签发和验真。

其他模块只能通过 API、事件或只读投影使用这些事实，不能直接修改拥有方数据库。

### 4.2 每场比赛一个逻辑报名数据集

“独立数据表”按业务语义实现为**逻辑数据集**，而不是动态物理表：

- `competition_registration_dataset`：一场比赛一条数据集定义。
- `competition_registration_dataset_row`：把报名记录绑定到数据集。
- 所有列表、导出、冻结和评审候选生成必须先解析数据集，再按 `dataset_id` 访问。
- `dataset_code` 可用于导出文件名、审计和归档，但不暴露连续主键。

这样既能实现隔离，也避免动态 DDL、迁移脚本膨胀、连接池元数据压力、跨表统计困难和 ORM/权限逻辑分叉。

### 4.3 核心事务短小，跨服务最终一致

一次报名确认只在报名服务本地事务中写报名、数据集行、快照和 Outbox；支付、消息、分析等后续动作通过事件完成。同步调用仅用于必须即时判定的查询，且应具备超时、熔断和明确降级。

### 4.4 快照优先于跨域联表

报名确认时保存团队、项目、成员和配置版本快照；评审批次创建时再保存候选与材料清单快照。历史记录读取快照，不回查当前主数据拼装历史。

### 4.5 定稿与发布分离

- **定稿（FINALIZED）**：内部确认结果已锁定，后续修改必须走重开流程。
- **发布（PUBLISHED）**：学生可见、晋级资格生效、消息触发。
- 发布前支持复核、抽查和审批；发布后必须保留版本与更正记录。

### 5.1 当前单体中的落位

近期不增加无必要的部署单元，在 `lumira-system` 内先形成以下包边界：

- `competition`：赛事与阶段配置，不再承载评审明细。
- `registration`：报名、数据集、快照、材料资格。
- `review`：新增评审完整领域。
- `expert`：专家档案和回避关系。
- `export`：异步导出与材料包。

模块间写操作通过应用接口或事件，不允许新增跨模块 `JdbcTemplate.update`。

## 6. 报名数据整改

### 6.1 数据模型

保留现有逻辑数据集，并补齐治理字段：

| 表 | 作用 | 关键字段/约束 |
|---|---|---|
| `competition_registration_dataset` | 赛事报名数据集定义 | `competition_id` 唯一、`dataset_code` 唯一、`schema_version`、`status` |
| `competition_registration_dataset_row` | 数据集与报名的稳定关联 | `dataset_id`、`registration_id` 唯一、`owner_user_id/uuid` |
| `competition_registration` | 报名聚合根 | `competition_id`、`dataset_id`、`team_id`、`project_id`、`status`、`version` |
| `competition_registration_snapshot` | 报名确认快照 | 报名/团队/项目/成员 JSON、配置版本、哈希 |
| `registration_material_submission` | 阶段材料提交 | `registration_id`、`stage_id`、`form_version_id`、`submitted_at` |
| `registration_material_value` | 字段值和文件引用 | `submission_id`、`field_key`、`file_id`、值类型 |
| `registration_eligibility` | 各阶段资格 | `registration_id`、`stage_id`、`status`、`source_review_batch_id` |

### 6.2 状态机

报名主状态建议统一为：

`DRAFT → SUBMITTED → PENDING_PAYMENT → PAID → CONFIRMED → FROZEN → COMPLETED`

旁路状态：

- `REJECTED`：资格审核不通过。
- `CANCELLED`：用户或管理员取消。
- `REFUND_PENDING / REFUNDED`：退款过程作为支付投影，不覆盖报名主状态。

每个状态转换必须记录操作者、原因、来源、时间和幂等键；禁止前端直接提交任意目标状态。

### 6.3 统一资料页面

页面入口建议保持 `/competitions/registrations`，主要功能：

- 必须先选择赛事，后续所有请求携带 `competitionId` 或 `datasetCode`。
- 列表展示报名编号、参赛编号、团队、项目、学生人数、材料数量、支付和报名状态。
- 抽屉/独立详情展示报名快照、团队快照、项目快照、成员快照、阶段材料和操作轨迹。
- 支持导出所选团队、导出当前筛选结果、生成全赛事材料包。
- 大于阈值（建议 1,000 个团队或 200 MB）自动转异步导出任务。
- 导出文件使用短时签名 URL，有效期默认 24 小时，下载写审计。

### 6.4 数据隔离规则

| 身份 | 可见范围 | 写权限 |
|---|---|---|
| 普通学生 | 本人创建或本人所属团队的报名 | 截止前按状态机编辑 |
| 团队负责人 | 本团队报名、成员和材料 | 管理本团队报名；成员移除需二次确认 |
| 赛事运营 | 授权赛事的数据集 | 查看、复核、导出；敏感字段按权限脱敏 |
| 评审专家 | 被分配任务的候选快照 | 仅填写自己的评分单 |
| 平台管理员 | 全租户或授权租户 | 管理与审计，默认不替专家改分 |

所有查询采用服务端数据范围谓词，不依赖前端隐藏。文件下载必须校验“文件引用属于当前可访问报名/评审任务”，不能只校验 `file:view`。

## 7. 评审领域完整设计

### 7.1 评审方案

每个赛事阶段创建一个评审方案，包含：

- 评审模式：单审、多人独立评审、会评、混合评审。
- 是否盲审、匿名字段规则和材料水印策略。
- 每个候选所需最少/目标专家数。
- 评分表版本与各评分项权重。
- 汇总算法：平均值、中位数、加权平均、去最高最低。
- 异常阈值：极差、标准差、缺评、零分/满分比例。
- 晋级规则：固定人数、分数线、比例、分组名额、同分处理。
- 接单截止、评分截止、补评截止和结果发布时间。

方案状态：

`DRAFT → READY → ASSIGNING → IN_REVIEW → AGGREGATING → FINALIZED → PUBLISHED → ARCHIVED`

### 7.2 评分标准版本

评分表必须版本化。发布评审批次时锁定版本，后续修改产生新版本，不能改变已创建批次。

评分项字段至少包括：

- 名称、说明、满分、权重、排序。
- 是否必填、允许小数位。
- 评分锚点（例如 0/5/10 分对应描述）。
- 是否允许专家备注、是否对参赛者公开。
- 否决项或合规项。

### 7.3 候选冻结

报名截止或运营点击“生成候选”时，报名服务产生不可变候选快照：

- 报名编号、匿名候选编号。
- 赛事、阶段、组别、赛道。
- 团队/项目/成员快照哈希。
- 材料文件 ID、文件版本、扫描状态和 SHA-256。
- 资格状态、支付确认状态。
- 快照生成时间和来源事件。

候选冻结后，团队仍可在允许的场景修改主资料，但不会自动改变本批次；确需替换材料时必须走“撤回候选 → 重新冻结 → 重新分配或保留原任务”的审计流程。

### 7.4 专家分配与回避

分配算法输入：

- 专家领域标签、赛道匹配度、历史评审质量。
- 专家可用时段、最大任务量、当前未完成任务。
- 学校/单位、团队、导师、项目的利益冲突关系。
- 同一候选的专家多样性要求。
- 历史改派和拒绝次数。

专家任务状态：

`ASSIGNED → ACCEPTED → DRAFT → SUBMITTED`

异常分支：

`DECLINED / EXPIRED / REVOKED → REASSIGNED`

系统自动分配后由运营确认；回避命中必须阻止分配。紧急人工覆盖需要填写原因并进入审计。

### 7.5 评分与提交

- 专家只能访问自己的任务和经过匿名化的候选快照。
- 评分单自动保存草稿，提交前校验所有必填项、合规项和总分。
- 提交后默认锁定；在截止前允许“申请撤回”，由评审管理员批准。
- 评审管理员可以查看完成率和异常，不应直接修改专家原始分。
- 如果必须更正，应保留原评分单版本和更正原因。

### 7.6 聚合、异常与仲裁

聚合过程先校验最少有效评分数，再按方案计算：

1. 排除已撤销、冲突或无效评分单。
2. 计算每项分数和总分的均值、中位数、极差、标准差。
3. 按配置去除最高/最低分，或采用稳健中位数。
4. 识别缺评、异常分、同分边界和否决项冲突。
5. 正常候选进入自动汇总；异常候选进入人工仲裁队列。
6. 仲裁只生成新的仲裁结论，不覆盖专家原始评分。

建议默认规则：

- 每个候选 3 名专家。
- 有效评分少于 2 份不允许汇总。
- 极差大于 20 分或标准差大于 12 分进入仲裁。
- 晋级边界同分不自动淘汰，进入人工确认。

### 7.7 定稿、发布与后续联动

定稿前检查：

- 所有候选满足最少评分数，或有豁免记录。
- 异常和同分边界已经处理。
- 晋级名额与分组规则校验通过。
- 发布名单与批次快照哈希生成完成。

定稿后写入不可变汇总，并可继续复核但不能直接改分。发布时：

- 报名服务接收晋级/淘汰事件并更新阶段资格。
- 消息服务向负责人/成员发送结果通知。
- 晋级团队获得下一阶段材料提交权限。
- 最终获奖结果触发证书服务生成候选批次。
- 分析服务更新赛事漏斗和评审质量指标。

## 8. 评审数据模型

### 8.1 新增核心表

| 表 | 说明 | 关键约束 |
|---|---|---|
| `competition_review_plan` | 阶段评审方案 | `competition_id + stage_id + version` 唯一 |
| `competition_review_criteria_version` | 评分表版本 | 发布后不可修改 |
| `competition_review_criterion` | 评分项 | 同版本 `criterion_code` 唯一，权重合计校验 |
| `competition_review_batch` | 一次候选冻结与评审运行 | `batch_no` 唯一，保存方案/算法快照 |
| `competition_review_candidate` | 候选快照 | `batch_id + registration_id` 唯一 |
| `competition_review_assignment` | 专家任务 | `candidate_id + expert_id + assignment_round` 唯一 |
| `competition_review_sheet` | 专家评分单 | 一次任务一个当前版本，提交后锁定 |
| `competition_review_score_item` | 评分项明细 | `sheet_id + criterion_id` 唯一 |
| `competition_review_aggregate` | 自动汇总/仲裁结果 | 保存统计值、算法版本、异常标记 |
| `competition_review_publication` | 定稿与发布版本 | 发布版本、名单哈希、审批与撤回信息 |
| `competition_review_appeal` | 申诉与处理 | 申请人、范围、结论、证据文件 |
| `competition_domain_event_outbox` | 可靠事件 | `event_id` 唯一、状态、重试次数 |

### 8.2 现有表的处理

`competition_stage_review_result` 不再承担专家原始评分。它保留为“阶段最终结果投影”或兼容旧页面的只读结果表：

- 数据来源改为已定稿/已发布的 `competition_review_aggregate`。
- 字段保留最终分数、晋级结论、公开评语和发布时间。
- 禁止新评审流程直接在该表录入单专家原始分。
- 旧数据迁移为一个 `LEGACY_IMPORT` 批次，并标记只有一份管理员评分。

### 8.3 通用字段

所有评审主表统一包含：

- `id`、业务 UUID。
- `tenant_id`、`competition_id`，必要时包含 `dataset_id`。
- `version` 乐观锁。
- `created_by/uuid`、`updated_by/uuid`、时间。
- `deleted` 仅用于草稿类数据；已提交评分和发布记录不物理删除。
- `trace_id` 或 `operation_id` 用于关联审计。

## 10. 权限、安全与合规

### 10.1 权限点

建议新增：

```text
review:plan:manage
review:batch:create
review:assignment:manage
review:task:view
review:score:submit
review:result:aggregate
review:result:finalize
review:result:publish
review:audit:view
registration:dataset:view
registration:dataset:export
registration:material:download
```

权限点必须进入主路由和角色权限目录，由角色管理统一授权，不能在页面内自建独立权限体系。

### 10.2 数据范围

权限判断同时包含：

- 功能权限。
- 租户范围。
- 赛事范围。
- 数据集范围。
- 任务/所有者范围。
- 字段级脱敏规则。

管理员“全部可见”应理解为在其租户与职责范围内全部可见；跨租户仍需平台级授权。

### 10.3 盲审与隐私

- 候选使用批次内匿名编号，专家端不返回团队、学校、导师、手机号、身份证等身份字段。
- 文档预处理移除 Office/PDF 作者、批注、修订和 EXIF；下载时可增加专家编号水印。
- 手机号、证件号等导出字段按权限脱敏；完整导出需要更高权限和用途说明。
- 记录查看、下载、导出、评分、改派、定稿和发布审计。
- 文件下载凭证一次性或短时有效，不暴露存储真实路径。

## 11. 一致性、可靠性与性能

### 11.1 事务与 Outbox

每个服务在一个本地事务中完成业务写入和 Outbox 写入。后台发布器异步投递，消费者按 `eventId` 幂等。失败重试采用指数退避，超过阈值进入死信队列并告警。

### 11.2 幂等

- 创建报名、支付订单、评审批次、专家分配、聚合、定稿、发布和导出都接收 `Idempotency-Key`。
- 数据库建立业务唯一键，不能只依赖 Redis 锁。
- 重复事件返回已有结果，不重复发送通知或签发证书。

### 11.3 并发控制

- 草稿保存使用乐观锁 `version`。
- 评审提交使用状态条件更新，避免重复提交。
- 定稿和发布使用批次级互斥与数据库条件更新。
- 汇总结果记录算法版本和输入评分单版本集合。

### 11.4 性能策略

- 报名列表使用覆盖索引：`dataset_id + status + created_at + id`。
- 材料详情按报名和阶段分页/懒加载。
- 导出和材料 ZIP 使用异步任务、分片读取和对象存储，禁止一次性加载全量到内存。
- 评审任务使用 `expert_id + status + deadline` 索引。
- 统计报表使用事件构建只读投影，不在核心表上做跨服务重查询。

### 11.5 建议 SLO

| 指标 | 目标 |
|---|---|
| 报名查询 API 可用性 | 月度 ≥ 99.9% |
| 评审提交 API 可用性 | 评审窗口 ≥ 99.95% |
| 评审提交 P95 | ≤ 800 ms（不含文件下载） |
| 结果发布事件生效 | 99% 在 60 秒内完成 |
| 事件丢失 | 0；允许重复但必须幂等 |
| 核心审计覆盖率 | 100% |

### 12.1 赛事运营端

建议在“赛事报名”或“数据管理”下保留以下页面：

## 13. 迁移与上线方案

### 13.1 阶段 A：边界加固

- 把报名新增写路径迁移到 Repository/Persistence Adapter。
- 为现有逻辑数据集执行幂等回填脚本，校验一赛一数据集、一报名一数据集行。
- 文件下载增加业务引用授权。
- 保留现有评审页面，但限制为兼容入口并增加审计。

### 13.2 阶段 B：评审 MVP

- 新建评审方案、评分项版本、批次、候选、任务、评分单和汇总表。
- 实现 3 专家独立评分、自动分配、回避、超时改派。
- 实现平均/中位数、异常检测、人工仲裁。
- 实现定稿与发布分离，以及晋级事件。

### 13.3 阶段 C：双轨与迁移

- 新赛事使用新评审流程。
- 历史未完成赛事可选择继续旧流程或一次性导入新批次。
- 旧 `competition_stage_review_result` 由新发布结果同步生成只读投影。
- 运行一个完整赛事周期后关闭旧写入口。

### 13.4 阶段 D：服务拆分

满足以下条件后优先拆出 Registration：

- 模块内部已无跨域直接 SQL。
- API/事件契约稳定并有契约测试。
- Outbox、幂等、监控、配置和发布流水线已经通用化。
- 数据量或发布节奏需要独立扩缩容。

随后拆出 Review。File、Payment、Message、Certificate 继续使用既有独立边界，不允许评审拆分时复制其主数据。

### 13.5 回滚策略

- 数据库升级全部幂等，先加表/加列，禁止同版本删除旧字段。
- 新旧流程通过赛事级 Feature Flag 切换。
- 发布前保留旧查询投影；关闭新写入即可回退 UI，不回滚已生成的审计数据。
- 事件消费者可暂停并重放，Outbox 记录不得在回滚时删除。
- 新流程结果未发布前可以作废批次；已发布只能创建更正版本。

## 15. 测试与验收

### 15.1 自动化测试

- 领域状态机单元测试：所有允许和禁止的转换。
- Repository 集成测试：唯一键、隔离谓词、并发更新。
- API 契约测试：版本兼容、错误码、幂等。
- 事件契约测试：字段、版本、重复投递、乱序投递。
- 权限测试：学生、负责人、专家、赛事运营、平台管理员。
- 文件授权测试：ID 枚举、过期 URL、越权下载。
- 聚合算法金丝雀数据集：均值、中位数、去极值、同分和异常。
- 导出测试：中文、公式注入、超大数据、断点与重试。

### 15.2 业务验收场景

1. 创建赛事后自动生成唯一逻辑报名数据集。
2. 两场赛事同一团队报名，查询与导出互不混淆。
3. 普通学生无法读取或下载其他团队资料。
4. 报名截止后生成候选快照；主资料变化不改变已冻结批次。
5. 有冲突关系的专家不能被分配。
6. 3 名专家独立评分，彼此不可见原始分。
7. 一名专家超时后可改派，旧任务失效。
8. 异常分进入仲裁，原始评分保持不变。
9. 定稿后不可直接改分；发布前学生不可见。
10. 发布后晋级团队自动获得下一阶段材料权限。
11. 结果事件重复投递不会重复通知或签发证书。
12. 大批量导出异步完成，下载可审计且会过期。

## 17. 风险与应对

| 风险 | 可能影响 | 应对 |
|---|---|---|
| 一次性拆分过多服务 | 交付延迟、故障面扩大 | 先模块化，按数据量和发布节奏拆分 |
| 动态物理表持续增加 | 迁移、统计、权限和运维复杂 | 统一逻辑数据集模型 |
| 旧评审数据语义不完整 | 历史报表口径不一致 | 导入 `LEGACY_IMPORT` 批次并显式标记 |
| 文件泄露 | 高合规风险 | 业务引用授权、短时 URL、盲审清洗、水印、审计 |
| 事件重复/乱序 | 重复晋级、重复证书 | 事件幂等、聚合版本、状态条件更新 |
| 专家不足或集中超时 | 评审延期 | 备用专家池、任务量上限、自动提醒和改派 |
| 算法争议 | 结果公信力下降 | 方案版本、模拟数据、公开规则、仲裁记录 |
| 大导出拖垮接口 | 影响报名和评审 | 异步任务、限流、分片、对象存储 |

## 附录 B：架构决策记录

| 决策 | 结论 | 原因 |
|---|---|---|
| 比赛隔离 | 逻辑数据集，不动态建物理表 | 隔离清晰，迁移、统计、权限和运维成本可控 |
| 微服务节奏 | 先模块化、后拆分 | 降低早期分布式事务和运维成本 |
| 跨服务一致性 | 本地事务 + Outbox + 幂等消费者 | 可追踪、可重试，不依赖长事务 |
| 历史数据 | 快照与版本 | 保证评审依据可复现 |
| 原始评分 | 不可覆盖，修改产生版本/仲裁记录 | 保证公平和审计 |
| 结果流程 | 定稿与发布分离 | 防止未经复核的结果直接生效 |
| 旧结果表 | 最终结果投影 | 兼容现有页面，不承载新评审明细 |
| 大导出 | 异步任务 | 避免浏览器和核心 API 资源耗尽 |
