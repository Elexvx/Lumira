# MySQL 季度恢复与故障演练手册

## 频率与范围

- 每月：检查快照、binlog 连续性、异地副本、对象锁、校验和与告警链路。
- 每季度：隔离环境完成一次全量恢复 + PITR，并验证核心业务。
- 每半年：执行一次主节点/可用区故障切换。
- 每年：执行一次跨区域恢复。

季度演练轮换场景：误删前 PITR、快照损坏后使用上一份快照、binlog 缺段检测、单可用区故障、凭据轮换后恢复、审计/Outbox 大表恢复性能。

## 演练准备

1. 建立演练工单，写明场景、目标 `RPO`、目标 `RTO`、数据范围和参与角色。
2. 使用生产备份的受控副本；敏感数据按合规要求脱敏，访问必须审计。
3. 隔离网络、数据库端点和对象存储前缀，确保演练应用不发送真实支付、短信、邮件或 webhook。
4. 锁定事故前应用提交、数据库版本和恢复工具版本。
5. 准备计时表，计时从宣布恢复开始，不能从数据库实例已经创建后开始。

## 演练步骤

1. 先按 [mysql-backup-and-restore.md](mysql-backup-and-restore.md) 随机选择一份逻辑备份，完成无写入校验和隔离恢复，证明发布门禁产物本身可用。
2. 随机选择一个符合保留策略的物理快照和快照之后的目标时间点，防止只练“最好恢复”的样本。
3. 校验快照清单、SHA-256、加密解密、GTID/binlog 起点和连续日志清单。
4. 严格按 [mysql-pitr-recovery.md](mysql-pitr-recovery.md) 恢复到隔离实例。
5. 在恢复完成但应用未启动时，运行 `bin/database-production-audit.mjs` 采集数据库证据。
6. 启动隔离的单个同步运行槽位，验证 `/api/health`、运行时版本和数据库版本。
7. 验证登录、权限、赛事报名、支付订单和回调幂等、文件引用、配置版本。
8. 验证 `platform_event_outbox`、`payment_event_outbox`、`plugin_event_outbox`、`event_consumer_receipt` 和 `async_task`。
9. 在禁用真实外部副作用的条件下恢复 relay，确认事件可重放、回执幂等且无新增死信。
10. 记录完成时间、实际 RPO/RTO和所有人工操作。

## 通过门禁

- 所选快照和完整 binlog 链不依赖生产主机本地磁盘。
- 能恢复到批准的目标 UTC 时间/GTID，且破坏事务边界验证正确。
- MySQL、schema/database version 和应用提交相容。
- 关键表行数、最大 ID、时间窗口抽样 checksum 和业务烟测通过。
- 业务记录与 Outbox 原子性通过，消费者重复执行不产生重复副作用。
- 实际 RPO/RTO 达标，告警通知到达当班人员。
- 恢复过程未使用生产管理员共享密码，临时凭据已回收。

任一关键门禁失败，演练结论必须是失败或有条件失败，不能写成“数据库恢复成功”。失败项要有负责人、截止时间和复测日期。

## 高可用演练回退边界

计划切换演练仅在维护窗口进行。新主库接受演练写入前可以直接恢复原端点；接受写入后禁止盲目切回旧库，必须先停写并证明反向同步或一致恢复完成。双主可写立即判定演练失败。
