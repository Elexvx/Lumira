# MySQL 高可用切换运行手册

## 目标

适用于托管 MySQL 8.4 双可用区实例，或已经通过独立评审的三节点 InnoDB Cluster。目标为单节点故障 `RPO <= 1 分钟`、`RTO <= 10 分钟`。实际承诺只能来自演练数据，不能来自产品宣传值。

Lumira 的 MySQL 是用户、权限、赛事、报名、支付、Outbox 和消费回执的持久化事实源。Redis Streams 是投递通道，因此切换顺序必须保护 MySQL 写入及 Outbox 一致性。

## 角色

- 指挥：决定开始、放弃、回退和恢复流量。
- 数据库操作员：只操作数据库 HA 控制面。
- 应用操作员：控制维护模式、Lumira 槽位、异步 relay 和健康检查。
- 记录员：记录 UTC/CST 时间、GTID、复制延迟、RPO、RTO 和每个门禁证据。

同一人不得同时执行高风险数据库操作并批准结果。

## 切换前门禁

所有条件必须满足：

1. 已冻结应用发布、DDL/Flyway、配置批量变更和数据修复任务。
2. 最近一次全量快照成功，连续 binlog 链完整；备份不是仅有“任务成功”状态，而是有最近一次隔离恢复证据。
3. 执行 [mysql-production-audit.md](mysql-production-audit.md)，确认 `log_bin`、GTID、ROW、耐久参数、复制线程和权限门禁。
4. 目标节点版本、参数、字符集、排序规则、时区与源节点一致。
5. 复制延迟小于批准阈值，且没有复制错误或待处理 DDL。
6. 有稳定数据库端点/代理；应用配置不直接固定某个节点 IP。
7. 当前 Outbox 待处理量、最老事件、死信数已经记录。
8. 回退负责人、观察窗口和“新主库接受写入后的回退方法”已经书面确认。

任一条件不满足，计划切换停止。真实主节点故障时可进入应急流程，但必须记录被跳过的门禁。

## 计划切换步骤

1. 宣布维护窗口开始，记录开始时间和当前应用槽位/运行版本。
2. 开启应用维护或停写；允许只读健康检查继续。
3. 暂停 Outbox relay、异步消费的数据库回写和调度器新任务。
4. 等待在途请求结束；确认连接池活动事务归零，没有超过 60 秒事务和锁等待。
5. 记录源节点最终 GTID/binlog 坐标、目标追平状态、Outbox 三张表的待处理/失败/死信统计。
6. 使用托管数据库控制面或经批准的 InnoDB Cluster 操作执行提升。不要在应用主机上拼接临时 SQL 或手工改复制元数据。
7. 等待稳定端点指向新主节点，并确认新主 `read_only=OFF`、`super_read_only=OFF`，旧主不可写。
8. 只启动一个 Lumira 同步运行槽位，清空旧连接池并建立新连接。
9. 验证 `/api/health`、运行时版本、数据库版本、登录、权限读取和只读业务查询。
10. 执行一笔批准的低风险幂等写入，验证同一事务产生的业务记录和 Outbox 记录一致。
11. 恢复 Outbox relay，确认待处理量下降、没有新增死信、Redis 消费与 MySQL 回执一致。
12. 恢复任务执行器，再逐步恢复全部用户流量。
13. 运行只读体检，记录复制拓扑、延迟和耐久参数。观察至少 30 分钟后结束窗口。

## 验收门禁

- 旧主不可写，只有一个写主。
- 应用全部连接到稳定端点，新旧连接没有混用。
- 关键表最大 ID/时间、抽样业务记录和最终 GTID 连续。
- 登录、赛事报名、支付幂等、文件引用、Outbox 投递、消费回执通过。
- Outbox 没有异常增长，死信没有增加。
- RPO 与 RTO 实测值达到目标；未达到时不得把演练标记为通过。

## 回退边界

**新主库尚未接受任何业务写入时**，可在确认复制方向和端点状态后将稳定端点切回旧主。

**新主库一旦接受业务写入，禁止盲目直接切回旧库。** 此时旧库已经分叉；必须先停写，由数据库负责人选择并验证反向复制、增量合并或基于备份/GTID 的一致恢复方案。不能用“应用看起来正常”代替数据一致性证明。

出现以下情况立即停写并进入该回退评估：双主可写、GTID 分叉、关键业务校验失败、Outbox 与业务记录不一致、支付幂等性异常或旧节点状态不明。

## 应急故障切换差异

源节点不可用时，不能等待源端最终坐标。记录最后可确认的副本应用时间/GTID 和最近 binlog 归档时间，以此计算数据丢失上界。提升后先保持维护模式，检查缺失事务、支付回调和外部系统重试，再恢复流量。真实 RPO 必须作为事故结论记录。
