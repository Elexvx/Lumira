# MySQL 容量、归档与分区运行手册

## 目标

在换库或盲目分库前，用真实增长率管理 MySQL 容量。重点对象包括三个 Outbox、消费回执、异步任务、登录/操作/安全审计、赛事通知 Outbox、平台更新任务、支付流水和文件元数据。

## 基线与预测

1. 每日固定时段执行 [mysql-production-audit.md](mysql-production-audit.md)，首份 JSON 为 baseline。
2. 后续使用 `--baseline` 与至少 24 小时前的同实例报告比较。
3. 记录数据字节、索引字节、估算行数、日增长和 30/90 天预测。
4. 同时记录磁盘总量、可用量、binlog/临时空间和备份空间；表容量不等于整个实例磁盘占用。
5. InnoDB `TABLE_ROWS` 是估算值。归档验收使用主键范围、时间窗口和抽样 checksum，不只看估算行数。

初始告警建议：磁盘 80% 警告、90% 严重，或按当前趋势 7 天内耗尽时严重；单表日增长超过过去 14 天中位数两倍时调查。阈值须在两周基线后调整。

## 数据生命周期建议

以下是讨论起点，必须由业务、法务和安全批准：

| 数据 | 在线保留建议 | 归档前置条件 |
| --- | --- | --- |
| 已投递 Outbox | 30–90 天 | 状态为终态、消费回执覆盖最大重放周期、无争议补偿任务 |
| Outbox 死信/失败 | 不自动归档 | 故障单关闭、已重放或明确放弃并留审计证据 |
| 消费回执 | 至少覆盖最大事件重放周期 | 与事件保留、幂等要求一致 |
| 异步任务终态 | 90 天 | 结果文件已进入受控对象存储，引用可追溯 |
| 登录/操作/安全审计 | 180 天或 1 年 | 以合规要求为准，法律保全优先 |
| 支付记录 | 按财务/监管期限 | 禁止仅因表大而缩短 |
| 文件元数据 | 跟随对象生命周期 | 数据库与对象存储必须成对校验 |

## 归档设计门禁

1. 明确表 owner、业务主键、终态定义、时间字段和法律保全规则。
2. 归档存储加密、版本化、不可变并有恢复工具；“导出成功”不是可恢复证明。
3. 归档批次有唯一批次号、主键起止、行数、checksum、创建时间和审批人。
4. 先复制到归档、验证可读与 checksum，再进入源端清理评审；两个动作不能在没有证据时串成一个不可恢复脚本。
5. 小批次执行，限制事务时间和锁影响，观察副本延迟、undo、binlog 和磁盘回收。
6. Outbox 只能归档终态；死信、处理中、claim 未过期或仍可能重试的数据不得归档。
7. 消费回执保留必须覆盖 Outbox/事件的最大重放窗口，否则重放会失去幂等保护。

## 执行流程

1. 在脱敏副本验证筛选条件、批大小、索引使用和恢复流程。
2. 生产低峰冻结相关 schema 迁移，创建并验证恢复点。
3. 生成候选主键清单和摘要，不以无界时间条件直接处理全表。
4. 复制候选数据到归档层，验证批次行数、主键连续性和抽样 checksum。
5. 业务 owner 和数据负责人批准源端清理批次。
6. 以短事务、可暂停的小批次执行清理；每批记录影响行数和延迟。
7. 运行只读体检，对比 Outbox、回执、任务、审计统计和磁盘趋势。
8. 在保留窗口内验证归档检索与恢复；观察期结束后关闭工单。

## 分区决策

只有同时满足以下条件才引入时间分区：表持续高速增长、主要查询和生命周期都以同一时间列界定、唯一键设计与 MySQL 分区约束兼容、现有查询能裁剪分区、归档/恢复演练通过。

分区不是索引替代品。先依据 Performance Schema digest 和 `EXPLAIN ANALYZE` 优化查询/索引，再决定分区。分区变更必须走迁移评审和副本演练，不能在生产临时执行。

## 回退边界

归档数据复制完成但源端尚未清理时，可放弃本批次并保留源数据。源端开始清理后，回退只能从已验证归档批次按主键恢复，并处理清理后产生的新写入；禁止直接用旧备份覆盖当前库。

若 checksum、行数、业务查询、复制延迟或 Outbox/回执门禁异常，立即停止后续批次。已经完成的批次保持原状并进入人工一致性评估，不继续自动清理。
