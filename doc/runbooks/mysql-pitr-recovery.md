# MySQL PITR 恢复运行手册

## 原则

PITR（时间点恢复）用于误删、错误 SQL、逻辑损坏或勒索事件。恢复链为“已验证全量物理快照 + 从该快照坐标开始的连续 ROW binlog”。目标为逻辑事故 `RPO <= 5 分钟`、`RTO <= 60 分钟`；区域级灾难目标可放宽到 `RPO <= 1 小时`、`RTO <= 4 小时`，以业务批准值为准。

**禁止直接覆盖当前生产实例。** 永远先恢复到隔离的新实例，在那里停止到目标时间/GTID并完成业务验证。

## 事故时间线

1. 立即冻结发布、DDL、批处理和人工数据修复。
2. 记录发现时间、最早异常时间、最后一笔确认正确的业务事务、外部支付/消息回调时间。
3. 如生产仍可读，保存当前 GTID、binlog 坐标、运行版本、数据库版本和只读审计报告。
4. 保全错误发生后的 binlog；不要因为“只恢复到更早时间”而丢弃后续日志，后续日志用于差异分析和补偿。
5. 由业务、数据库和安全负责人共同确定恢复目标时间。时间必须明确时区，并预留安全边界，避免刚好落在破坏事务中间。

## 恢复前门禁

- 全量快照校验和、MySQL 版本、创建时间、GTID/binlog 起点和加密密钥可用。
- 从快照起点到目标点的 binlog 连续，无缺段、无重复、无校验失败。
- 隔离实例网络不接收生产应用写入，不运行 Lumira async/job/Outbox relay。
- 目标实例字符集、排序规则、时区、`lower_case_table_names` 和关键 InnoDB 参数匹配。
- 恢复操作者与验收者不同；全过程有审计记录。

## 恢复步骤

1. 创建隔离 MySQL 8.4 实例，禁止生产应用和外部回调访问。
2. 使用云厂商物理恢复或已批准的 MySQL Shell/物理备份流程恢复全量快照。
3. 校验实例版本、数据库名、快照 GTID、关键表存在性和快照完成标记。
4. 按顺序校验并重放 binlog，只重放到批准的 UTC 时间或明确 GTID 边界。不得依据本地时区口头时间直接停止。
5. 目标点到达后立即保持实例不可写，并记录最终 GTID、最后事件时间和恢复耗时。
6. 在隔离网络启动一个与事故前提交一致的 Lumira 同步运行槽位；保持 async/job/relay 关闭。
7. 验证数据库版本、关键表行数/最大 ID/抽样校验和、用户与权限、赛事报名、支付订单/回调幂等、文件对象引用、配置版本。
8. 比较三个 Outbox、消费回执和异步任务：确认恢复点前事务完整，恢复点后的外部副作用列入补偿清单。
9. 业务负责人批准数据点后，按高可用切换手册把稳定端点切到恢复实例。
10. 先恢复同步 API，再恢复 Outbox relay，最后恢复任务执行器和外部回调。持续观察重复投递和幂等冲突。

## PITR 正确性检查

- 目标破坏事务不存在，目标时间前最后一笔正确事务存在。
- 业务记录与同事务 Outbox 同时存在或同时不存在，不出现半边状态。
- 已发送但恢复点后数据库中不存在的外部副作用已识别，例如支付成功回调、短信/邮件、文件上传。
- 恢复点后合法写入有补偿方案，不能静默丢弃。
- 抽样 checksum 必须在业务主键和时间窗口上执行，不能仅比较 `COUNT(*)`。
- 恢复实例上重新执行只读体检，PITR/耐久和权限门禁通过。

## 切换与回退边界

恢复实例接受生产写入前，可以放弃该实例并恢复原生产端点。

恢复实例接受生产写入后，禁止盲目切回旧库。旧库、事故库和恢复库可能形成三个数据分支；必须停写并由数据库负责人依据 GTID 和业务补偿记录决定唯一事实源。

若恢复验证失败，保留隔离实例和日志用于分析，重新从原始不可变快照创建新实例；不要在失败实例上反复叠加不透明修复。

## 演练记录

必须记录：快照标识、binlog 起止、目标 UTC 时间/GTID、实际 RPO、实际 RTO、恢复数据量、验证人、失败检查和补偿事项。只有完成业务验证的恢复才算成功，不以“数据库进程已启动”作为完成。
