# ADR-0007：报名采用规范化值和不可变快照双模型

## 状态

Proposed

## 背景

赛事报名需要支持每个赛事不同的团队、项目、成员和自定义字段。现有实现已经保存多个 JSON 快照，适合证据留存和旧数据兼容，但不适合作为字段筛选、统计、权限和大批量导出的长期主读取模型。

同时，报名成员角色只是某次提交中的业务字段，不能与 IAM 的系统角色混用。正式 Team/Project 主数据也不能覆盖某次报名的历史提交内容。

## 决策

- `competition_registration` 保持报名聚合根。
- 团队、项目、成员提交内容进入报名域自己的子表；正式 Team/Project 只作为可选 source 引用。
- 动态字段按 subject 和 field_key 写入 typed value 表，核心高频字段保留规范化列。
- 字段定义包含稳定 key、scope、type、version、sensitivity 和 exportability。
- `member.role` 存在于报名成员/字段值模型，与 `sys_role` 没有外键或权限语义。
- 现有 snapshot JSON 长期保留为不可变证据和兼容回退，不作为批量查询与导出的主数据源。
- 迁移采用双写、回填、checksum 和影子读取后切流。

## 影响

### 正面

- 自定义字段可以独立存储、按字段授权、筛选和导出。
- 报名历史不受正式 Team/Project 后续修改影响。
- 快照仍能支持争议审计和旧数据恢复。

### 负面

- 写入表数和事务复杂度增加。
- 动态宽表导出需要 provider 批量聚合值。
- 双写期需要持续一致性对账。

### 中性

- JSON 不被完全移除，而是从查询主模型转为证据模型。

## 备选方案

### 所有字段只存 JSON

开发快，但大规模字段查询、统计和导出成本不可控，拒绝作为长期方案。

### 所有赛事字段都加物理列

无法支持多样化赛事和频繁配置变化，拒绝。

### 把报名团队直接写为正式 Team

会混淆业务快照和正式主数据，并产生未经确认的团队记录，拒绝。
