# Lumira 开发实施路线与阶段落地清单

## 1. 文档定位

本规范用于统一大型 SaaS 系统脚手架从方案阶段进入正式开发阶段后的实施顺序、阶段目标、模块优先级、依赖关系、里程碑划分、阶段性交付物与验收标准。

它不是架构补充说明，而是整套平台底座的实施蓝图。

说明：本文档保留了分阶段实施视角，但阅读时要以当前仓库已落地事实为准。当前主线已经具备 `lumira-server + lumira-async + lumira-job-executor + api-proxy` 运行拓扑、系统管理主链路、AI、文件、消息、插件、国际化、支付、平台配置与基础部署能力，因此文中“第一阶段/第二阶段”更多用于回顾建设顺序和规划后续增强，不再表示当前仓库仍停留在对应早期阶段。

## 2. 实施原则

- 先底座，后业务。
- 先统一，后扩展。
- 先主链路，后增强。
- 先可靠，后丰富。
- 先可运行，后大规模铺开。

## 3. 总体阶段划分

建议分为六个阶段：

1. 脚手架底座建设阶段。
2. 系统管理核心模块建设阶段。
3. 平台运营与租户治理阶段。
4. 异步任务、文件中心与审计增强阶段。
5. 高可用、高并发、监控与运维强化阶段。
6. 业务模块快速复制与平台化扩展阶段。

## 4. 阶段目标总览

### 4.1 第一阶段

完成前端主壳层、后端认证体系、多租户上下文、RBAC 权限骨架、统一接口规范、统一页面模板、统一缓存与会话、基础日志与审计、统一文件上传入口、异步任务骨架和基础部署能力。

### 4.2 第二阶段

完成系统管理基础模块，包括用户、角色、菜单、部门、岗位、字典、配置、租户切换、审计日志查询、登录日志查询等。

### 4.3 第三阶段

完成平台运营与租户治理相关能力，包括租户管理、租户套餐、租户域名、租户配额、租户初始化、租户状态控制、平台级管理视角和平台管理员审计能力。

### 4.4 第四阶段

完成任务中心、导入导出规范化、文件中心元数据化、消息中心基础能力和更多审计增强。

### 4.5 第五阶段

完成高可用增强、限流、降级、熔断、监控、压测、告警、灰度发布、回滚、备份恢复演练等能力。

### 4.6 第六阶段

进入业务模块快速铺设阶段，新增业务模块应主要围绕既有模板和底座能力复制展开。

## 5. 第一阶段定位

第一阶段不是简单做登录页和几个菜单，而是交付一套真正能承载后续开发的基础平台。

第一阶段必须至少做到：

- 前端有统一壳层和统一页面模板。
- 后端有统一认证、租户、权限和请求处理机制。
- 前后端有统一接口规范和统一错误码。
- 缓存、日志、审计、任务、文件留好标准入口。
- 项目能本地启动、测试环境部署、完成基础联调。

## 6. 第一阶段实施顺序

建议严格按以下顺序推进：

1. 完成项目初始化与工程骨架。
2. 完成认证与租户上下文。
3. 完成权限模型与菜单路由联动。
4. 完成前端主布局和统一页面模板。
5. 完成系统管理最小闭环。
6. 补日志、审计、缓存、文件、任务的骨架接入。
7. 完成部署、联调、自测与阶段验收。

## 7. 第一阶段详细工作包

- 建立 `common`、`infrastructure`、`modules` 等模块化目录。
- 接入统一异常处理、统一返回结构、统一日志上下文、数据库连接、Redis 连接、基础配置体系和数据库脚本管理工具。

前端完成：

### 7.4 前端主布局与统一页面模板

### 7.5 系统管理最小闭环

## 8. 第一阶段任务分组与验收口径

为避免第一阶段执行时只看阶段标题、不看落地边界，第一阶段建议进一步拆成九个任务组推进，并按组验收。

### 8.1 任务组一：工程初始化与基础骨架

目标：

- 建立前后端标准工程骨架
- 建立统一目录、统一配置、统一运行方式
- 建立统一基础依赖和基础入口

核心任务：

- 前端完成项目初始化、标准目录、统一请求入口、基础路由与异常页
- 后端完成项目初始化、模块化目录、统一返回结构、错误码、异常处理与迁移工具接入

验收口径：

- 前后端都能独立启动
- 目录结构符合规范
- 后端存在统一 API 返回结构
- 前端存在统一请求封装入口

### 8.2 任务组二：数据库与后端基础设施初始化

目标：

- 落地第一阶段底座表结构
- 完成后端最小基础设施封装

核心任务：

- 建立租户、用户、组织、角色、菜单、字典、配置、日志、文件、任务相关核心表
- 接入 Redis 基础封装
- 建立租户上下文容器骨架
- 接入 `traceId`
- 建立统一分页对象和分页结果结构
- 建立审计字段自动填充骨架

验收口径：

- 数据库初始化脚本可执行
- 核心底座表可正常建表
- 后端存在统一分页模型
- 日志上下文可输出 `traceId`
- Redis 可正常连接并完成基础读写

### 8.3 任务组三：认证与租户上下文

目标：

- 建立登录、会话、当前用户、当前租户、租户切换闭环

核心任务：

- 后端实现登录、登出、刷新 token、当前用户、当前租户、可访问租户列表、租户切换
- 建立 Redis 会话存储与登录日志记录
- 前端完成登录页、登录态恢复、未登录跳转、租户展示与租户切换

关键约束：

- 租户切换必须调用后端接口并刷新上下文
- 一个用户可以属于多个租户
- 租户切换后必须重载权限与菜单

验收口径：

- 用户可以登录系统
- 登录后可获取可访问租户列表
- 可切换租户且切换后上下文立即生效
- 登录和切换行为都有日志记录

### 8.4 任务组四：权限模型与菜单快照

目标：

- 建立 RBAC 权限骨架、权限快照、菜单树和按钮权限统一接入

核心任务：

- 后端实现角色、菜单、用户角色、角色权限、权限快照、菜单树和接口鉴权骨架
- 前端基于权限快照生成菜单、控制页面访问、实现按钮权限组件

关键约束：

- 前端菜单显隐不能代替后端鉴权
- 所有按钮权限统一使用 `permission_key`
- 菜单、按钮、接口权限标识必须统一

验收口径：

- 登录后菜单根据权限变化
- 按钮根据权限变化
- 后端接口存在基础权限拦截能力
- 租户切换后菜单与按钮权限重新计算

### 8.5 任务组五：前端主壳层与基础模板

目标：

- 建立统一主布局、统一页面骨架和统一高频组件

核心任务：

- 建立主后台布局、设置布局、AI 布局和登录入口布局
- 建立 `TenantSelector`、`QueryPanel`、`ActionBar`、`DataTable`、`DetailDrawer`、`PermissionButton`、`EmptyState`
- 建立统一列表页、表单页、详情页模板

关键约束：

- 尽量只让核心内容区滚动
- 查询区、操作区、表格区、详情区结构必须统一
- 弹窗和抽屉使用规则要统一

验收口径：

- 至少一类标准列表页模板可复用
- 布局中已集成租户切换、用户菜单、通知入口占位
- 新增一个标准管理页时不需要重写布局容器

### 8.6 任务组六：系统管理最小功能闭环

目标：

- 用系统管理模块验证整套底座真的能跑通

建议优先完成：

- 用户管理
- 角色管理
- 菜单管理
- 部门管理
- 字典管理
- 配置管理
- 登录日志
- 操作日志

每个模块最低要求：

- 列表页
- 新增/编辑
- 详情查看或抽屉查看
- 状态切换
- 权限控制
- 分页查询
- 统一响应结构
- 租户隔离
- 审计记录

验收口径：

- 用户管理可完成新增、编辑、状态切换
- 角色管理可完成菜单授权
- 菜单管理支持树结构
- 字典与配置可正常读取与修改
- 日志页可查询登录日志和操作日志

### 8.7 任务组七：日志、审计、缓存、文件、任务骨架

目标：

- 接入第一阶段必须存在的平台能力入口

核心任务：

- 建立统一 `traceId`
- 建立操作日志与登录日志记录能力
- 建立字典缓存、配置缓存、权限快照缓存和租户切换后缓存刷新能力
- 建立统一上传接口和 `file_object` 元数据落库能力
- 建立任务表、任务查询接口和任务详情接口

验收口径：

- 关键请求有 `traceId`
- 关键写操作能在审计日志看到
- 字典和配置具备基本缓存
- 文件上传可用且元数据可查
- 任务表和任务接口存在

### 8.8 任务组八：响应式适配与多端基础策略

目标：

- 建立桌面端、平板端、移动端的基础适配能力

核心任务：

- 建立响应式断点和设备判断 hook
- 建立桌面端管理页主形态
- 建立平板端查询区压缩与低频列降级策略
- 建立移动端卡片化或全屏层退化策略

验收口径：

- 主布局在桌面端和平板端可正常工作
- 查询区和高频页面在窄屏下不发生严重错位
- 详情层、弹窗层和操作区具备可触控退化方案

### 8.9 任务组九：联调、自测、文档与部署

目标：

- 完成从开发到底层部署说明的闭环

核心任务：

- 完成前后端联调
- 完成基础自测
- 完成环境变量模板、数据库初始化说明、Redis 启动说明、联调地址规范
- 完成部署脚本或 Docker Compose 说明

验收口径：

- 本地环境可按文档启动
- 测试环境具备可部署能力
- 文档足以支持研发、测试和运维协作

## 13. 第一阶段验收标准

### 13.1 前端验收

- 布局是否统一。
- 页面模板是否统一。
- 菜单是否随权限变化。
- 租户切换是否刷新上下文。
- 按钮权限是否可控。
- 响应式是否基本成立。

### 13.2 后端验收

- 认证是否稳定。
- 租户上下文是否生效。
- 接口鉴权是否统一。
- 日志审计是否能查。
- 缓存是否基本可用。
- 异常返回是否统一。
- 数据库脚本是否规范。

### 13.3 系统链路验收

必须验证以下完整路径：

- 用户登录
- 进入默认租户
- 菜单按权限显示
- 打开用户管理列表
- 新增/编辑用户
- 分配角色
- 修改角色菜单后重新进入页面
- 日志中能看到关键操作记录
- 切换租户后菜单和数据边界变化

## 14. 第二阶段衔接方式

第一阶段完成后，不建议立即大规模铺业务，而应先补齐系统管理细节，把已有模块打磨到足够稳定、足够标准。

第二阶段的本质是对第一阶段骨架做结构验证。

## 15. 推荐开发组织方式

建议按“底座能力包”推进，而不是前后端完全割裂。

推荐能力包：

- 认证与租户能力包
- 权限与菜单能力包
- 统一页面模板能力包
- 系统管理能力包
- 日志与审计能力包
- 文件与任务骨架能力包

## 16. Codex 实施硬约束

- 任何新增页面必须基于统一模板。
- 任何新增接口必须遵循统一响应结构、统一错误码和统一分页结构。
- 任何租户级数据操作必须自动带租户上下文。
- 任何按钮权限必须前后端同时接入。
- 任何导入导出能力不得同步直跑，必须预留任务化路径。
- 任何缓存必须按统一 key 规范实现。
- 任何关键写操作必须记录审计日志。
- 任何页面响应式逻辑必须基于统一断点体系。
- 任何代码提交都不得破坏已完成的主链路闭环。

## 17. 第一阶段常见错误预警

- 过早铺页面。
- 前端先行过头。
- 后端只做接口不做基础设施。
- 把多租户做成表里加 `tenant_id` 就算完成。
- 第一阶段不做部署与运行说明。

## 18. 里程碑定义

建议第一阶段拆成四个里程碑：

1. 工程骨架可运行。
2. 登录与租户闭环打通。
3. 权限与菜单闭环打通。
4. 系统管理最小闭环完成。

## 19. 实施结论

这份实施路线的核心，是把前面所有技术方案从“原则和设计”转化成“明确的开发顺序与交付边界”。

第一阶段必须聚焦底座，不贪多，不乱铺，不跳步骤。只有底座站住，后续平台运营模块、业务模块、高可用增强、异步任务增强和多租户运营能力才能真正顺滑展开。
