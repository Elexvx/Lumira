## 5. 测试过程

### 5.1 第一阶段：准入检查与冒烟测试

首先确认测试环境可访问、赛事处于已发布状态、管理员具备赛事和角色管理权限，普通用户能够正常登录。

执行步骤：

1. 在两个相互独立的浏览器会话中分别登录 Administrator 和 Common User。
2. 刷新两个会话，确认登录状态不串号。
3. 对比两个账号首页问候语、菜单和可见入口。
4. 使用普通用户直接访问 `/user-center/roles`。
5. 确认普通用户跳转 `/403`，且无法加载角色管理内容。

该阶段同时验证了会话隔离、菜单级权限和路由级权限，避免只依赖前端菜单隐藏形成“看似有权限控制”的假象。

### 5.2 第二阶段：后台配置与学生端映射

管理员端依次检查赛事名称、类型、级别、参赛范围、收费方式、金额、货币、团队人数上限、成员字段、报名文书和初赛材料配置。

随后切换普通用户，在学生端报名向导中逐项核对：

- 可选赛事与后台发布状态一致。
- 赛事名称和描述一致。
- 收费口径和人数计算一致。
- 最小、最大团队人数一致。
- 姓名、学校、性别字段的启用、必填和顺序一致。
- 报名承诺书与知情同意内容一致。
- 初赛材料配置能够被学生端正确识别。

### 5.3 第三阶段：动态字段同步测试

动态字段测试采用“新增—刷新—填写—保存—删除—再次刷新”的闭环。

执行步骤：

1. 管理员新增“临时同步测试字段”。
2. 刷新后台，确认字段仍存在，证明配置已持久化。
3. 普通用户刷新团队步骤，确认表头和编辑输入框出现新字段。
4. 填写“同步成功”，保存成员。
5. 返回管理员端删除临时字段。
6. 普通用户刷新页面，确认新字段消失，姓名、学校、性别和原有值均保留。
7. 检查赛事配置没有测试字段残留。

### 5.4 第四阶段：报名正向和逆向流程

报名流程按照向导步骤顺序执行：

1. 打开赛事报名列表并进入新增报名。
2. 选择已发布赛事。
3. 在未确认协议时点击下一步，验证系统阻止继续。
4. 依次确认全部协议，验证可以进入团队步骤。
5. 不添加成员直接下一步，验证最小人数校验。
6. 添加有效成员并保存。
7. 在项目步骤留空项目名称，验证必填提示。
8. 填写项目名称和简介，验证项目和报名记录创建成功。
9. 在没有材料表单配置的情况下，验证系统能够进入支付确认前步骤并展示可理解的空态。
10. 在没有可用支付方式时，验证“立即支付”按钮被禁用。

逆向测试采用“故意不满足前置条件”的方式，重点观察按钮是否被正确阻止、加载状态是否结束、错误提示是否明确，以及是否发生重复创建或错误跳转。

### 5.5 第五阶段：缺陷复现、定位、修改与部署

每个缺陷均按以下流程处理：

1. 固定账号、赛事、页面、输入和前置条件。
2. 记录实际结果、错误码、浏览器表现和接口行为。
3. 根据错误发生位置定位到前端路由、过滤器、控制器、应用服务、事务或本地存储逻辑。
4. 编写或补充针对性自动化测试。
5. 修改代码并完成构建或部署。
6. 使用原始复现步骤回归。
7. 执行受影响模块全量或定向测试。
8. 记录修复证据、剩余限制和发布建议。

## 7. 发现问题与修改过程

### 7.1 HIS-001：后台新增学生失败（P1）

#### 问题复现

管理员在后台创建新的普通学生时，创建流程失败，或创建后的角色绑定不正确。

#### 根因分析

1. 角色查询引用了不存在的字段。
2. 关联表 upsert 使用的列名存在歧义。
3. 事务内异步读取无法看到刚写入的新用户。

#### 修改方式

1. 修正角色查询字段引用。
2. 明确关联表 upsert 的列名和写入顺序。
3. 调整事务内读取逻辑，确保用户创建、启用和角色绑定使用一致的事务视图。

#### 修改后结果

历史线上已成功创建并启用测试学生，角色绑定正确；当前 `SystemUserManagementAppServiceTest` 47/47 通过。

### 7.2 HIS-002：普通学生无法创建报名项目（P1）

#### 问题复现

Common User 在项目步骤填写合法的项目名称和简介并提交，接口在进入项目控制器前返回 `A0403`。

#### 根因分析

全局敏感词过滤器在扫描所有写请求时，错误要求用户拥有 `plugin:sensitive-words:view` 后台词库查看权限。普通学生没有该管理权限，因此合法报名请求被提前拦截。

#### 修改方式

1. 敏感词词库查看和管理权限仍只对管理员开放。
2. 已登录可信用户的表单提交继续执行敏感词扫描，但不再要求后台词库查看权限。
3. 输入框实时敏感词检查与提交时检查使用同一套规则。
4. 对敏感词管理接口和普通业务写接口分别执行权限判断。

#### 修改后结果

普通学生创建项目线上回归通过；敏感词服务、控制器、表单过滤器和请求体过滤器历史测试 40/40 通过；当前相关定向测试 42/42 通过；赛事报名服务和控制器 59/59 通过。

### 7.3 HIS-003：不同账号恢复同一报名草稿（P1，数据隔离）

#### 问题复现

账号 A 保存报名草稿后退出，账号 B 登录并进入相同报名入口，系统恢复了账号 A 的报名步骤、团队或项目数据。

#### 根因分析

报名草稿使用全局固定 localStorage key，所有账号读取同一份本地数据。

#### 修改方式

1. 将草稿存储键升级为按登录用户 ID 分区的 v2 key。
2. 停止读取旧的公共草稿 key，避免旧数据继续造成串号。
3. 访问与当前用户不匹配的后续步骤时回退到第 1 步。

#### 修改后结果

线上刷新和账号切换验证通过；草稿键隔离测试 2/2 通过，未发现跨账号数据恢复回退。

### 7.4 HIS-004：成员表格少字段时出现横向滚动（P2）

#### 问题复现

当赛事只配置两个成员字段时，成员表格仍出现不必要的横向滚动，部分内容或操作区域需要额外拖动才能查看。

#### 根因分析

原实现存在以下布局约束：

- 表格最小宽度固定为 760px。
- 字段列最小宽度为 160px。
- 表格使用固定布局。
- 操作列固定宽度和内容宽度之间存在冲突。

#### 修改方式

1. 表格最小宽度改为根据实际配置字段数量计算。
2. 表格布局从 fixed 改为 auto。
3. 字段列最小宽度调整为 120px。
4. 操作列保持 148px，保证编辑和删除操作不换行且可见。

#### 修改后结果

当前代码和自动化证据显示修复已生效，生产版本也确认包含修复提交。但由于生产浏览器会话退出，尚未完成同一登录状态下的最终截图复验，因此该问题标记为“代码已修复、视觉验收待闭环”。

错误位置：`lumira-ui/src/auth/sessionLifecycle.ts:31`。

原因是 `buildLogoutRedirectTarget` 的默认参数直接读取 `window.location`，而 Vitest 当前运行在 Node 环境中。该问题目前表现为测试环境兼容性问题，但会阻塞前端全量测试 100% 通过，也使登出逻辑缺少可靠的自动化回归保障。
